# requirements-map

狙い: 人がレビューするのは判断であって、事実の一覧ではない。判断の構造を先に見せ、根拠は「どう調べたか」まで添えて、疑ったところだけコードを開けばよい形にする。どの案にするかは人が決めるので、AI は推さず、軸ごとの比較までを出す。

## decision.json

| 項目 | 書くこと |
|---|---|
| background | 背景。3行まで。経緯は「日付 に 何が決まった」を → でつなぐ |
| question | 決めること。材料（資料・議事録）にある言葉をそのまま使う |
| question_then | 任意。question の答え次第で続けて決めること。1つずつ短い名詞句の配列（例: ["受け取る側の登録方法", "株主番号・郵便番号の扱い"]）。ページでは question と並べて箇条書きにする |
| axes | 判断の軸。`id` と `label`。ふつうは「開発工数」「リスク（その論点で一番起きてほしくないこと）」「先方の要望との合い方」の3つ。論点に合わせて言い換えてよい |
| options | 案。`id` `label` `note`（任意の一言）と、`eval`（軸ごとの評価。`{"軸の id": {"text": "API はある[F1]が、ミニアプリの画面が無い[F2]"}}`。根拠は支える節の直後に `[F1]` と書く。文中に書けないときだけ `grounds`。`short` はカードで軸ごとに太字で出す16字までの一言で、「小: 設定を変えるだけ」のように軸の上での位置がひと目でわかる言葉にする） |
| if | 見積が要る案を選んだ場合に出てくるもの。見積が要る案が1つなら1つのオブジェクト、複数なら案ごとのオブジェクトの配列。各オブジェクトは `option`、`estimate`（見積に入るもの）、`ask`（先方に聞くこと）。どれも `label`・`grounds`・`why`（なぜ要るか1文。「今は〜なので」）。見積の項目には任意で `when` |
| evidence | 根拠のファイル（code-evidence の evidence.json）への相対パス |
| asis | asis を呼んだときだけ。今の仕組みの要素（`link` `elements` `diagram`）。下の「asis を呼んだときの欄」を見る |
| gaps | asis を呼んだときだけ。制御の単位と、要望の操作ごとのずれ（`unit_now` `unit_want` `rows`） |
| open | 任意。決めていないこと（この比較に入れていない論点）。短い文の配列。上限と字数は tour.py。[F1] は書けない |
| changes | asis を呼んだときだけ。要素 × 案で、その案を選ぶと要素がどうなるか。`{"要素の id": {"A": "そのまま", "B": "..."}}`。全部のマスを埋める |

- 案は同じ高さの選択肢だけを並べる。ある案を前提にした話は `if` に入れる
- 今のままにする選択が現実にありうるとき（仮着地がある、先方が検討しているなど）は、その案も入れる。label は「何をするか」を動詞で終える
- `eval` は全部の案に全部の軸を書く。良し悪しの言葉（良い・悪い・おすすめ）は使わず、その軸で何が起きるかを書く。根拠が言えるところは、支える節の直後に `[F1]` を書く。short は必須（tour.py が検査する）
- AI が推す案は書かない
- `if` は、見積が要る案に付ける。見積が要る案が複数あれば、全部の案に付ける（1案だけに付けると、その案を推したように見える）。見積の項目は「作るもの」を名詞で、聞くことの項目は「先方が答える問い」を「〜か」で終える
- 聞くことの答え次第で入る見積の項目は `when` に条件を書く（例: 受け取る人を株主に限るなら）
- 聞くことの grounds は、その問いが必要になる今の挙動（例: 今は誰でも受け取れる）。why はその挙動を「今は〜なので」と1文で書く。ページでは項目の下に小さく常に出る
- 根拠の無い項目には、なぜ無いかを `note` に書く
- 事実は、案や項目の判断が乗っているものだけを立てる。網羅的な洗い出しはしない（asis が集めた事実は別。同じ evidence.json に入るが、上限の数には入れない）
- asis の要素は、To-Be で移し先を決める要素だけにする。changes の表で、どの案がどの要素に手を入れるかが一目でわかることが狙い。カードの軸の評価は、この表の結果として読めるように書く
- 背景と決めることは材料にあることだけ。無ければ聞く

asis を呼んだときの欄:

- `asis.link`: asis.md への相対パス。tour.py が読み、ページの最後に畳んで埋め込む
- `asis.elements`: 要素ごとに `id` `name`（実装の名前）`role`（働きの一言）`text`（働きの1文。[F1] 必須）。`flow`（`{"t": 箱, "no": 止まるときの行き先}` の配列）は diagram が無いときの小さな流れ図
- `asis.diagram`: 構成図のインライン SVG。あると要素のカードの代わりに、この図と番号つきの一覧を出す（flow は見ない）。図の中の番号 ①②… は elements の順。class は box / gate / data / t / s / ng / lane / ar / ar feed（破線）/ head
- `gaps.unit_now` / `unit_want`: 今の仕組みが決めている単位と、要望が決めたい単位。「今の仕組み」の先頭に並べて出す
- `gaps.rows`: 要望の操作ごとに `want` `where`（その操作がある入口・場所）`now`（今止められるか。[F1] 必須）。案はこの表の行をどう埋めるかとして読める
- [F1] を書けるのは eval の text、elements の text、gaps の now、changes のマス、asis.md だけ。それ以外の欄（label、why、role、want など）に書くと NG

## 量の上限

人と話しながら使える量にするため、tour.py が数と字数を検査する（上限は tour.py の `LIMITS` と `CHARS` が正本）。背景3行、軸3つ、案3つ、見積5つ・聞くこと4つ（どちらも案ごと）、事実10個（案と、選んだ場合の項目が引くもの。asis・ずれ・changes・asis.md が引く事実は数えない）、asis の要素6つ・流れ図の箱4つ・ずれの行6つ・決めていないこと5つまで。カードの全文（eval の text）は45字。超えたら削るか、論点を分ける。

## ページの形

tour.html の雛形が決めるので、decision.json では変えられない。中身を書くときに、どこに何が出るかを知っておく。

- 1枚だけ。大見出しに決めること、中見出しで背景・決めること（どちらも箇条書きで畳まない）・案・見積が要る案ごとの「X を選んだ場合」・（あれば）決めていないこと
- 案は、料金表のプランのように案ごとのカードを横に並べ、軸ごとに short を太字、その下に全文（[F1] 付き）。ホバーで隠さない
- 「X を選んだ場合」は、作るもの・先方に聞くことの項目の下に why を出す。根拠の無い項目は note を出す
- 根拠は奥に置く。普通に読むときは文中の番号と印（✓ AI 確認済み / 資 資料のみ / △ 確認が足りない）だけ。番号を押すと右のパネル（狭い画面では下のシート）にその事実を出す。本文の文は光らせない（光るのはパネルのコードの行だけ）。パネルは 主張 → 確かめ方の印 → AI が確認したこと → 調べ方・資料 → 畳んだ範囲・コード・検索。パネルは最初から本文に重なる広い幅で開く（「狭める」「広げる」で切り替え）。Esc か「閉じる」で閉じる
- カードの見出しの下に、その案の根拠の内訳（✓5 資2 など）を出す。押すと、その案の根拠の一覧が開く
- カードの全文は short で言い切り、理由を1文で足すだけにする
- asis を呼んだときは、決めることの次に「今の仕組み」（制御の単位 → 構成図 → 要素ごとの1文）、「要望と今の仕組みのずれ」（要望の操作ごとの表）、「案が今の仕組みをどう変えるか」（要素 × 案の表）を出す。asis.md はページの最後に畳んで埋め込むので、tour.html 1枚で完結する（Shelf にはこれだけ上げる）。表示には CDN（highlight.js、marked、mermaid）を使うので、オフラインでは asis.md は生の文字、mermaid の図は描かれない

## 調べる範囲

最初に、論点に関わるリポジトリを全部挙げる。利用者の画面、店舗やお客様の画面、API、ミニアプリなど、その機能に触れうる側を漏らさない。例: toypo なら toypo-api、toypo-app、toypo-web、toypo4store-web、toypo4store-app、toypo-lma-builder が候補。迷うものは範囲に入れ、検索して 0 件なら「検索して 0 件」と残す。

## 手順

1. 材料を読み、背景と決めることを書いて見せる。ここがずれていると後が全部ずれるので、確認を取ってから進む
2. 決めることが既存の仕組みを変える・置き換える・広げるものなら、asis を呼んで今の仕組みを洗い出し、見せる。案はその要素と働きの上に立てる。機能を使うか・作るかの論点では呼ばない
3. 案・軸・`if` の項目を書く。各項目について「これが言えるか」を code-evidence に渡す。code-evidence は根拠を集め、別の AI の確認まで済ませて返す。asis を呼んだときは同じ evidence.json に足し、asis で確かめた事実はそのまま引く
4. ページを作る。NG が出たら直す
   ```
   python3 ~/.claude/skills/requirements-map/scripts/tour.py <decision.json>
   ```
   量の上限、軸の評価の抜け、short の抜け、根拠の id、文中の [F1] と grounds の食い違い、根拠も note も無い項目、根拠があるのに why が無い項目、asis・ずれ・changes の欄の抜けと根拠、[F1] を書けない欄を検査し、code-evidence の照合を --strict で通す。確認が済んでいない事実（確認の後に中身を変えたものを含む）があると作らない
5. `open <tour.html>` で開いて見せる

## 置き場所

指定がなければ、作業中のリポジトリの `docs/plans/<題>/` に decision.json・evidence.json・tour.html を置く。asis を呼んだときは asis.md も同じ場所に置く（tour.py が読んでページに埋め込む）。
