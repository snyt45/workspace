# asis

狙い: As-Is を読んだ人が「今そうなっている」と腹落ちし、そのまま「これを To-Be でどこへ移すか」を考え始められる形にする。

そのために、仕組みは名前や定義からではなく、読まれる場所から説明する。名前は作った人の意図で、読まれる場所は今の事実だから。例: `OwnerStaff` は「オーナー権限」という名前だが、読まれる場所をたどると、オーナー用 API の門、フロントの出し分けに使う `is_owner`、全店舗の権限を作るきっかけ、の3つとして働いている。ここまで言えると、To-Be で決めることは「この3つをそれぞれどこへ移すか」だとわかる。

読む人は、全体像を先に押さえてから細部へ進む。細かい事実は、全体像のどの軸に属するかを示してから書く。全体像に収まらない事実が出たら、事実を例外に逃がす前に全体像の方を直す。

## 進め方

- **判定の種類を一掃する（要素を選ぶ前に）。** 対象の領域で「誰に何をさせるか」を決めているコードを、名前に頼らず機械的に並べる。例: before_action の一覧（名前ごとの件数）、`raise ResourceForbidden` のような拒否の全箇所、主体のモデル（Staff / StoreStaff など）の述語メソッド（`toypo_staff?`、`primary_admin?`）、機能フラグの判定。並べたものを「何を決めているか（答える問い）」で束ね、束を軸にする。余ったものは新しい軸か例外にする。To-Be で触らない軸も落とさない（触らないと決めたこと自体が To-Be の情報）
- **全体像の表を書く。** 軸ごとに1行。列は「答える問い」「正本のデータ」「読む場所（件数）」「状態」「To-Be で触るか」。状態は 現役 / 遺物（新しく書く経路が無く、残った行だけが読まれる）/ 書けるが読まれない / 読まれるが書けない のどれか。状態を言うには、作る経路の有無・最後に書かれた時期・読む場所が生きているか、の3つを確かめる。時期は DB でしか分からないので、実行した SQL と結果を根拠（code-evidence の sources）にする
- **要素を選ぶ。** To-Be で「置き換える・残す・消す」を決めることになるものだけを挙げる。材料（前の調査メモ、資料、ER図）は出発点にするが、そのまま写さない
- **読み手を漏らさず探す。** 名前の検索で見えない経路（関連や別名を通した参照、フロントへの受け渡しとその先）までたどり、対象に触れうるリポジトリは全部見る。コメントや材料が「使われていない」と言っていても、検索で確かめる
- **書き手も並べる。** 要素のデータについて、どこから書けるか（API のアクションと permit、画面、console / rake、コールバック）を全部挙げ、画面から通るか・API だけか・経路が無いかを書く。移行では読み手より先に書き手を止めることになるので、読み手の表と対で置く
- **制御の単位を言う。** 今の仕組みが「何を単位に」決めているか（例: どの入口に入れるか、どの行を読めるか）を1文で書く。要望が別の単位（例: どの操作をしてよいか）で語られているなら、そのずれを As-Is の先頭に置く。同じ言葉（権限など）で単位が違うと、案を読んでも腹落ちしない
- **働きで束ねて、1文で言い切る。** 読み手を「何として働いているか」（門、範囲、表示、生成など）でまとめ、束ごとに「X は Y として働いている」と書く。これが本文になる。束から外れる読み手は本文に混ぜず、例外に分ける
- **図で見せる。** 要素ごとに、その働きが効く流れを小さな図にする。分かれ道では、通るときと止まるときの両方を描く。冒頭に、要素どうしの関係がわかる全体図を置く
- **確かめる。** 束の1文を1つの事実として code-evidence に渡す。読み手・書き手の表の行も、どれかの事実の根拠（evidence か searches）に入れる。入れられない行や、材料から写しただけの行は「未確認」と書く。確認が済むまで完成にしない

## asis.md

読んだ人が、制御の単位 → 全体像の表 → 全体図 → 要素ごとの「働きの1文・図・読み手の一覧・書き手の一覧」→ 例外 → 追記 の順に読めるようにする。

- 要素の見出しは、名前だけにせず働きを添える（例: 「X: Y の入口と、Z のきっかけ」）
- 全体像の表は decision.json の asis.overview にも写す（requirements-map のページで「今の仕組み」の先頭に出る）
- 読み手の一覧は、To-Be で1行ずつ移し先を決める表になる。働きと場所がわかるように書く
- 読み手・書き手の「場所」は、画面から始まる操作なら「画面のパス → コントローラー#アクション」まで書く。「店舗用 API の中」のような粗さでは、読む人が自分でたどり直すことになる
- 本文の1文の末尾に、根拠の事実の番号 `[F1]` を付ける。最後に evidence.json の場所を書く
- 図は mermaid で書く（GitHub と Obsidian で表示できる）。要素どうしの流れを1枚で見せる構成図は、requirements-map のページ用に SVG でも描く（decision.json の asis.diagram。番号 ①②… は elements の順、class は requirements-map の SKILL.md にある）
- 良し悪しや To-Be の提案は書かない。どこへ移すかは requirements-map で比べる

## 追記（asis.md ができた後）

asis.md ができた後の質問や新しい発見は、会話だけで答えて終わりにしない。

- 答えは、全体像の軸と要素の名前、[F 番号] で位置づける（例: 「これは軸 3『身分』の話で、要素 OwnerStaff の読み手の1つ」）。会話で新しい切り口を作らない
- asis.md に無い事実は、evidence.json に事実を足して確認を済ませ、asis.md の該当する軸・要素の表に行を足す。末尾の「追記」に日付と要点を1行残す
- 全体像に収まらない事実が出たら、軸を足すか軸の切り方を直し、decision.json の asis.overview も直す。例外に逃がすのは、軸には収まるが束の1文から外れるものだけ

## 置き場所

指定がなければ、作業中のリポジトリの `docs/plans/<題>/asis.md` と `evidence.json`。requirements-map は同じ evidence.json から、判断に効く事実だけを引く。
