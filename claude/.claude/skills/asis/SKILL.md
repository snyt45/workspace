# asis

狙い: As-Is を読んだ人が「今そうなっている」と腹落ちし、そのまま「これを To-Be でどこへ移すか」を考え始められる形にする。

そのために、仕組みは名前や定義からではなく、読まれる場所から説明する。名前は作った人の意図で、読まれる場所は今の事実だから。例: `OwnerStaff` は「オーナー権限」という名前だが、読まれる場所をたどると、オーナー用 API の門、フロントの出し分けに使う `is_owner`、全店舗の権限を作るきっかけ、の3つとして働いている。ここまで言えると、To-Be で決めることは「この3つをそれぞれどこへ移すか」だとわかる。

## 進め方

- **要素を選ぶ。** To-Be で「置き換える・残す・消す」を決めることになるものだけを挙げる。材料（前の調査メモ、資料、ER図）は出発点にするが、そのまま写さない
- **読み手を漏らさず探す。** 名前の検索で見えない経路（関連や別名を通した参照、フロントへの受け渡しとその先）までたどり、対象に触れうるリポジトリは全部見る。コメントや材料が「使われていない」と言っていても、検索で確かめる
- **制御の単位を言う。** 今の仕組みが「何を単位に」決めているか（例: どの入口に入れるか、どの行を読めるか）を1文で書く。要望が別の単位（例: どの操作をしてよいか）で語られているなら、そのずれを As-Is の先頭に置く。同じ言葉（権限など）で単位が違うと、案を読んでも腹落ちしない
- **働きで束ねて、1文で言い切る。** 読み手を「何として働いているか」（門、範囲、表示、生成など）でまとめ、束ごとに「X は Y として働いている」と書く。これが本文になる。束から外れる読み手は本文に混ぜず、例外に分ける
- **図で見せる。** 要素ごとに、その働きが効く流れを小さな図にする。分かれ道では、通るときと止まるときの両方を描く。冒頭に、要素どうしの関係がわかる全体図を置く
- **確かめる。** 束の1文を1つの事実として code-evidence に渡す。読み手の表の行も、どれかの事実の根拠（evidence か searches）に入れる。入れられない行や、材料から写しただけの行は「未確認」と書く。確認が済むまで完成にしない

## asis.md

読んだ人が、制御の単位 → 全体図 → 要素ごとの「働きの1文・図・読み手の一覧」→ 例外 の順に読めるようにする。

- 要素の見出しは、名前だけにせず働きを添える（例: 「X: Y の入口と、Z のきっかけ」）
- 読み手の一覧は、To-Be で1行ずつ移し先を決める表になる。働きと場所がわかるように書く
- 本文の1文の末尾に、根拠の事実の番号 `[F1]` を付ける。最後に evidence.json の場所を書く
- 図は mermaid で書く（GitHub と Obsidian で表示できる）。要素どうしの流れを1枚で見せる構成図は、requirements-map のページ用に SVG でも描く（decision.json の asis.diagram。番号 ①②… は elements の順、class は requirements-map の SKILL.md にある）
- 良し悪しや To-Be の提案は書かない。どこへ移すかは requirements-map で比べる

## 置き場所

指定がなければ、作業中のリポジトリの `docs/plans/<題>/asis.md` と `evidence.json`。requirements-map は同じ evidence.json から、判断に効く事実だけを引く。
