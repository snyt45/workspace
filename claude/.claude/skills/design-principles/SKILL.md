# 設計の原則（design-principles）

ユーザーがレビューで繰り返し見ている、設計の個人基準。原則は上から順に見る。
上の原則がクリアなら、残りは細かい指摘として扱い approve する。

AI で作ったコードは、やりたいことは動いていても、知識が書いた手近な場所に置かれていることが多い。
なので差分の1行ずつより先に原則を見る。

## 原則

### 1. 知識は、それを知っている層に1か所だけ置く

判定・条件・パラメータの対応表・文言は、その中身を本来知っている層に置く。同じ知識を2か所に持たない。
2か所にあると、片方を変えたときにもう片方の直し忘れが起き、そこが不具合や抜け道になる。

- 確かめ方：「これを変えたら何か所直すか」「直し忘れたら何が起きるか」
- ずれを埋める修正が続いているなら、置き場所が原因と疑う
- 判定を呼ばれる側の奥に置くと、判定の結果（スキップした・失敗した）が呼び出し側に伝わらない。結果が一致しない・失敗が黙って消える不具合の多くはここから出る

例：
- 認証の総当たり対策で、どのエンドポイントが何を照合し宛先はどのパラメータか、をミドルウェアの定数とコントローラの両方が持っていた → 照合の中身を知っているコントローラ側で宣言する（toypo-api#2273）
- 期限切れの判定を発行の直前に置いて `next` でスキップ → 通知が飛ぶ・無関係なクーポンを返す。候補一覧を作る側の scope に寄せ、8か所を3か所にする（toypo-api#2242）
- エラーを後から付け替えるのではなく、文言を持っている `devise.ja.yml` を直す（toypo-api#2292）
- サブクラスだけの知識は親に集めず、サブクラスで override して宣言する（toypo-api#2204）

### 2. 依存は一方向にする。汎用の層は具体の層を知らない

ミドルウェア・SDK のラッパー・共通部品は、アプリの中身（コントローラ・パラメータ・画面遷移）を知らない。
具体の層が汎用の層を使う向きだけにする。

- 分け方：「アプリの中身を知らなくても判定できるものは汎用の層、照合の対象や結果を知っている必要があるものはコントローラやモデル」
- 汎用の層から具体の層へ働きかけたいときは、イベントを出して具体の層が購読する

例：
- rack-attack にはパスもパラメータも見ない量の遮断（`ban heavy ips`）だけを置き、認証の回数制限はコントローラに `rate_limit` と同じ形で宣言する（toypo-api#2273）
- LiffClient は SDK の薄いラッパーにして画面遷移を持たない。期限切れは `tokenExpired` を出し、遷移は Register、再認証の状態は Provider が持つ（toypo-lma-builder#197）

## 使い方

### レビュー時

1. 狙いはまず認める（「狙いはその通りだと思います」）
2. 差分が足した知識（判定・条件・対応表・文言）を挙げ、原則に上から順に照らす
3. ずれていれば、行ごとに指摘を並べるのではなく、何をどこに置くかの全体像（表）で示す。形が大きく変わるなら、PR を分けるかクローズするかまで提案する
4. そのうえで細かい不具合を見る。置き場所を直せば消える指摘は、個別に書かずに置き場所の指摘にまとめる

### 開発時

書く前に「この判定は誰が知っているべきか」「この層は何を知らずにいるべきか」を決めてから置く。
動いた後に、各原則の確かめ方を自分のコードにかける。
