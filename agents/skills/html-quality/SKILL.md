# HTML 品質向上（html-quality）

技術文書・設計資料系の HTML（設計比較、レビュー資料、解説記事など）を、初見の読者が迷わず読める品質に上げる。

## 使い方

1. 対象 HTML を読む（生成直後 or 既存ファイル）
2. 下記チェックリストでレビューし、各項目に pass / fail を付ける
3. fail を**読者への影響が大きい順**に修正する
4. 修正後に再レビューし、全項目 pass を確認する
5. 完了報告は修正内容を列挙する（何を・なぜ直したか）

## チェックリスト

### A. 構造・情報階層（最初に見るべきものが最初にある）

- [ ] **結論が最初**にある（ヘッダー直後。タイトルを開いて3秒で「何を選ぶべきか」が分かる）
- [ ] 結論 → サマリー → 詳細の順（読者が途中で離れても判断材料は手に入る）
- [ ] `h1 → h2 → h3` の見出し階層が正しく、飛びがない（`h2` の次に `h4` が来る等がない）
- [ ] 各セクションが1つのトピックに絞られている

### B. 自己完結性（会話コンテキストを排除）

- [ ] 固有名詞・バージョン・アプリ名などの前提が**本文中で定義**されている（会話でしか知り得ない前提を本文で使っていない）
- [ ] 「前述」「§x 参照」「上記の通り」のような**内部参照がない**（必要ならその場で一言説明）
- [ ] 省略語・社内用語の初出に説明がある

### C. 情報量の制御（詰め込みすぎない）

- [ ] 1セクションにコードは**最大1つ**、補足（note）は**最大1つ**
- [ ] メリット/デメリットは各**5個まで**（重要度順）
- [ ] 表は10行以内に絞られている
- [ ] 1画面に伝えようとしているメッセージが1つ（複数の話題が混ざっていない）

### D. 図解・視覚化（文章で読むより図が早いもの）

- [ ] データフロー・構造の違い・関係性は**図**（SVG / Mermaid / テキスト図）で表現されている
- [ ] 図はラベル付きで、図だけ読んで構造が分かる

### E. 表現（箇条書き・表・文体）

- [ ] 3行以上の連続した文章がなく、箇条書き・表で整理されている
- [ ] 比較・対比は表を使っている
- [ ] 結論ファーストの文（「理由 → 結論」でなく「結論 → 理由」）

### F. センス（デザイン）

- [ ] 配色が一貫している（アクセント色は1〜2色。推奨・警告の意味づけが統一）
- [ ] 余白が適切（行間・セクション間・パディング）
- [ ] フォントサイズ・太字の階層が統一されている
- [ ] モバイル幅で崩れない（グリッドは折り返す等）
- [ ] 過剰な装飾がない（情報を伝えるための装飾だけ）

### G. 一貫性

- [ ] 用語が統一されている（案の呼び名、エンドポイント表記）
- [ ] 結論と各セクションの記述が矛盾していない
- [ ] 数値・工数・日付が同じ意味で使い回されていない

### H. 技術的な正確性・妥当性

- [ ] コードスニペットが実コードと一致している（雰囲気コードは「イメージ」と明記）
- [ ] ファイルパス・エンドポイント・型名が実在する
- [ ] HTML のタグが正しく閉じられている（レンダリング崩れがない）

## 修正の優先度

1. **読者が誤った判断をするリスク**（矛盾、事実誤認、結論と本文の不一致）— 最優先
2. **読めないリスク**（構造崩れ、自己完結性の欠如、情報過多）— 次
3. **読みにくさ**（長文、図解不足、センス）— 最後

修正はファイルを直接編集し、ブラウザ（Plannotator 等）で表示して確認する。

## 呼び出し元スキルへの注意

system-design-discuss 等の生成スキルから呼ぶ場合は、**生成直後にこのチェックリストでレビューする**。レビュー結果はユーザーに報告してから修正に入る。
