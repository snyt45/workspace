# summary / 呼び出し経路 / 処理の流れ

## summary

機能の核心主張を1〜2文で。核心はここに1回だけ書く（entry の note や fig のキャプションで再掲しない）。

## entry（呼び出し経路）

対象コードは単体では理解できない。どこから呼ばれどう到達するかを必ず示す。形は生態系に合わせて選ぶ。

- **Rails 等のサーバサイド**: ルーティング → コントローラ → 対象（`stack`。各段に file:line）
- **React 等のフロントエンド**: エントリ/ルーティングからのコンポーネント階層（`tree`。対象の位置に `here`）
- **CLI・スクリプト**: 起動手段（task定義・alias・bin・cron）→ 対象（`stack`）
- **プラグイン・設定（Neovim 等）**: 読み込み機構（require元・keymap・autocmd・イベント）→ 対象（`stack`）
- **ライブラリ/gem**: 利用者が呼ぶ公開API → 対象の内部経路（`stack`）

経路は実物を辿って書く（routes.rb・エントリファイル・task定義を実際に読む。創作しない）。入口が複数あるなら主要なものだけ。
`note` は「◯◯をすると」レベルの短文を改行区切りで並べる（1行1事実。詳述しない）。

## flow（処理の流れ）

入口の呼び出しを受けた**実際のコード経路**を追う。spec の実行例でなく、実ファイルのメソッド遷移。実値はそのステップが触れるコード内の値。
各ステップに行参照 `l` を付ける。5ステップ以内が目安。超えるなら代表例の粒度が大きすぎる。

## 整合チェック

flow・issues・trace に書いた用語や数字は、その答えになる注釈が該当行にあるか確認する。読んで湧く疑問がその場で解消できなければ注釈を足す。
trace に書いた意外な実値も、その理由を担う注釈があるか確認し、その `ex` は結果を実際に決めた実データで書く（実在する別例で代用しない）。
