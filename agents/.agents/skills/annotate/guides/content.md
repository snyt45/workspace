# コード解説（注釈でない依頼）の組み立て

「この構文を解説して」など、注釈でなく解説が求められた場合の構成。**言語非依存**。対象言語の概念（所有権・借用相当・型・参照・エラー処理・パッケージ管理等）は、その言語の対応概念に置き換えて適用する。

## 構成（依頼に応じて必要なものだけ使う）

1. **結論** — 質問への答えを最初に短く。例: 「`&str` は文字列を参照する型です」
2. **コード例** — 最小限に。質問と無関係な機能を混ぜない。変数名をわかりやすく
3. **動きの説明** — 重要な部分だけ。複雑な処理は分解して流れを示す（`入力 → 処理A → 処理B → 出力`）。必要なら中間の型・値も
4. **なぜ？** — 言語・ランタイムの設計思想。「コンパイラ/ランタイムから見るとどう見えるか」の視点を入れる。エラーが出る場合は「この言語は何を防ごうとしているのか」まで
5. **比較** — 似た概念と違い。単に列挙せず「どんな場面でどちらを選ぶか」まで。例: 値型と参照型、`==` と `===`、コールバックと Promise/async
6. **メンタルモデル** — 概念を捉える図（ASCII図可）。図は「内部実装を完全に表す簡略図」と明示する
7. **実践的な慣習** — 「動く」だけでなく「この言語・この用途ではどちらが一般的か」。例: 引数に参照型を取るのが慣例など
8. **悪い例と良い例** — 理解に役立つ場合だけ。「これは意図的に間違った例」と明記して対比
9. **一歩踏み込むと** — 内部仕組み・パフォーマンス・メモリ・よく使われるパターン・標準ライブラリの設計思想。本題より長くしない
10. **コラム** — 関連する面白い豆知識。必要な場合だけ

## 原理

- 専門用語は初出で1文説明する。「coercion が発生します」で終わらせない。変換・解決の仕組みがあるなら「自動変換される仕組み」と一言添える
- 優先順位: まず動き → なぜそうなるか → 言語らしい書き方 → 深い仕組み。最初から内部表現・IR・最適化の話に行かない。質問に直接関係する場合か、深掘りされた場合だけ
- パフォーマンスは根拠なく「速い/遅い」と断定しない。対象が値型か参照型か、アロケーションが起きるかでコストは変わる
- 複数の書き方があるなら、おすすめ → 別解 → それぞれの違い。初心者向けのわかりやすい方を先に、実務でよく使われる方を後で
- 学習用の小さな例で `unwrap()` 相当（無視してよいエラー簡便法）を禁止しない。ただし実アプリでの失敗モードを説明し、必要なら堅牢な書き方も示す
- 「危険」とだけ言わずに済むもの（unsafe相当・グローバル状態等）は「安全チェックの一部をプログラマが責任を持って保証する仕組み」と説明する
- ユーザーのコードには、いきなり別コードで答えない。問題箇所 → なぜ問題か → 最小限の修正 → 必要なら改善版
- リファクタリングは「短くなるから」だけを理由にしない。可読性・設計・エラー処理・パフォーマンスの観点から
- 初学者の質問を否定しない。回避策が存在するなら、コストと使う場面を説明する
- 誤解されやすい構文は隣接する書き方との対比で示す（`'\t'` と `"\t"` 等。注釈ルールと同じ）

## 出力

解説はそのまま回答として出力する（ファイル生成・HTML化はしない）。必要な場合だけ「結論 → 本文」の順。

# 注釈の中身

文章はすべて `$essence` に従う。結論ファースト、1文1情報、事実ベース、ノイズ排除。

## 出力形式

注釈は `plannotator review` の codeAnnotation として実差分に注入する。1注釈 = 1コメント。API 操作は `$plannotator-review` に委譲する（draft JSON の codeAnnotations）。

- アンカー: 差分内の該当行（新しい側、`lineStart`〜`lineEnd`）。差分に無い行の注釈（既存コード・diff外の構文）は、それが使われている差分行に置く。ファイル全体への注釈は `scope:"file"`（`lineStart`/`lineEnd` = 1）
- `text`: 下記「カード」。**Markdown で整形する**（plannotator は注釈テキストを Markdown 描画し、太字・引用・リンク・インラインコードにスタイルが付く）:
  - タイトル: 1行目を `**...**` で太字に
  - 本文: 文ごとに改行
  - 例（ex）: `> ` 引用ブロックで（旧カードの ex 枠に相当）
  - ref: `[表示名](URL)` リンクで
- `conventionalLabel` / `severity`: 注釈は説明でありレビュー指摘ではない。カスタムラベルで種別を示す（設定不要でバッジ表示される）:
  - 概要 → `overview` / `info`
  - 呼び出し経路 → `entry` / `info`
  - 処理の流れ → `flow` / `info`
  - 構文注釈 L2 → `warning` / `info`（知らないと推測不能）
  - 構文注釈 L1 → `note` / `info`（誤読・罠）
- 絵文字は使わない。種別はラベルバッジで示す
- `author: "ai-annotate"`。公式リファレンスは text 末尾に URL を1行

## 注釈の種類と配置

- **概要** (`overview`): 差分の1個目のファイルにファイル全体コメント（`scope:"file"`）として置く。機能の核心を1〜2文。核心はここに1回だけ書く
- **呼び出し経路** (`entry`): 対象コードの入口になる行に置く。実物を辿って書く（routes・エントリ・task定義を実際に読む。創作しない）。`◯◯ → ◯◯ → 対象` の経路を1行1事実で
- **処理の流れ** (`flow`): 概要と同じ差分1個目のファイルにファイル全体コメント（`scope:"file"`）として置く。実際のコード経路を5ステップ以内で。各ステップに該当行の参照を付ける
- **構文注釈** (`warning` / `note`): 該当行に置く（下記「警告レベル」）

同じ構文が複数ファイルに出現する場合、完全版（what/ex/ref）は初出に1つだけ置き、他は「その行の変更で何が起きるか」を自己完結で2〜3文に畳む。「◯◯の注釈参照」だけの注釈は作らない（レビューでは参照先を探せない）。

## 実データ

変数に実際に入る値を、リポジトリの実ファイル構成・schema・fixture・設定から特定する（創作しない）。不明なら安全なコマンドで確認する。
`ex` は必ずこのリポジトリで実際に流れる値。机上の創作例は不可。

## カード（what / ex / ref）

- `what`: 正確な操作記述1〜2文。1文目が結論。
- `ex`: 実例（入力→出力）で腹落ちさせる。`> ` 引用ブロックにする。出力は評価値に限らず、そのコードが生む具体物（解決されるパス・発動するキー・作られるレコード等）でよい。
  - 多段パイプラインは最終出力だけでなく中間状態も示す。
  - 実例に一般則を1句添える（例だけだと読者が帰納の責任を負う）。文字クラス・パターン系は非ASCII境界例（日本語・空白）を1つ含める。
- `ref`: 公式リファレンスの該当セクションURL。確信があるURLのみ。うろ覚えなら公式トップに落とす。捏造URLは信頼を壊す。リンクだけでよい。読者が次に調べたいであろう箇所には多めでよい。

## 書き方のルール

- 1文1情報。短い文に分ける。
- わかりやすさのための言い換えで曖昧になるなら正確な方を取る（例: `:h` は「親ディレクトリを返す」ではなく「末尾のパス名要素を取り除く」）。
- コールバックや非同期APIは、呼び出し自体が返す値とコールバックに渡る値を分けて書く（戻り値を受けようとするのが定番の事故）。
- 紛らわしい構文は隣接する書き方との対比で（`'\t'` と `"\t"` は2文字のまま。タブになるのは `$'\t'` だけ）。順序に意味があるガードは、入れ替えたら何が壊れるかを1行で。
- スコープ境界の依存を明示する。対象外を指す識別子（コマンド名文字列・グローバル・他ファイル定義のキー等）は、定義元パスと不在時の失敗モードを⚠か既存カードの1文で。
- 変数が暗黙に生まれる場所（`read var`・コールバック引数・キャプチャ）は「ここで var が作られる」と注釈する。
- コメントや文字列中の他ファイル参照は、その正体を1行で解決する。
- 類推のダメ押し・由来・うんちくは書かない。
- 外部APIの注釈は全引数を列挙せず、この行の実引数での結果 ex 1行を優先する。

## 警告レベル

基準は「主流言語の汎用知識だけで意味を推測できるか」。対象言語固有でない構文（POSIX/bash共通・C系共通）は下げる。迷ったら上に倒す。

- **L2 🔴** (`issue`): 知らないと行の意味が推測できない、または見た目から想像する挙動と実際が乖離するもの。
  例: zsh `${(s:/:)v}` `*(N/)`、Ruby `&:sym`、Rails の暗黙マジック、TS `infer`・mapped type、Terraform `[*]`・`dynamic`、JS `Proxy`
- **L1 🟡** (`suggestion`): 読めるが誤読や罠があるもの。
  例: クォート有無で挙動が変わる、`-e` と `-L` の違い、JS `==`、Go `defer` の引数評価タイミング
- 汎用知識で読める行には何も付けない。目安: 構文注釈は1PRあたり5〜15個。
- 見た目は普通だが実行環境に接続された暗黙挙動（Neovim `vim.g`、Rails callback）も L2。
- 構文でなく引数の意味が推測不能な場合も対象。外部APIに渡す裸の `true`/`false`/`nil`/数値フラグは、何を切り替えるかを一言。

## 仕上げのセルフチェック

- 各注釈が読者が実際に質問したはずのことに答えているか。他の注釈で自明になったものは削る。
- 🔴 は1機能あたり8〜9枚が目安。全事実が他の 🔴 + 相互参照1句で導出できるなら 🟡 へ降格。導出できない同系カードは1枚に統合。
- 不慣れな言語は L2 を厚めに `ref` 付きで。慣れた言語は注釈を絞り、`処理の流れ` と既存コードの罠を充実させる。
- 1注釈の text は3〜6文が目安。長くなるなら分割して該当行に散らす。
