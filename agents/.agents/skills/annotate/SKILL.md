# Annotate

対象コードに、紙に印刷して書き込みながら理解していくときのような注釈を付けた自己完結HTMLを生成する。全行解説ではない。必要なところにだけ書き込む。言語は問わない。
読者は経験のあるエンジニア。AIが書いたコードや不慣れな言語を読む機会が多く、「この構文は何で、実際どんな値が入るのか」を毎回質問してきた人。その質問を先回りして潰す。

## 警告レベル

基準は「主流言語の汎用知識だけで意味を推測できるか」。対象言語固有でない構文（POSIX/bash共通、C系共通など）はレベルを下げる。迷ったら上に倒す。

- **L2 警告 🔴** — 構文を知らないと行の意味自体が推測できない、または見た目から想像する挙動と実際が乖離するもの。→ 欄外カード
  - 例: zsh `${(s:/:)v}` `*(N/)`、Ruby `&:sym` `method_missing`、Railsの暗黙マジック、TS `infer` やmapped type、Terraform `[*]` や `dynamic`、JS `Proxy`
- **L1 注意 🟡** — 読めるが誤読・罠があるもの。→ ホバーで一言メモ
  - 例: クォート有無で挙動が変わる、`-e` と `-L` の違い、JS `==`、Go `defer` の引数評価タイミング
- 汎用知識で読める行には何も付けない。目安: L2はユニーク構文数で5〜15個/100行（短いファイルは比例でよい）。
- 「見た目は普通のコードだが実行環境に接続されている」暗黙挙動（Neovimの `vim.g`、Railsのcallback等）もL2の対象。
- 構文でなく**引数の意味**が推測不能な場合も対象: 外部APIに渡す裸の `true`/`false`/`nil`/数値フラグは、その引数が何を切り替えるかを一言注釈する（意味を持つ `nil` 渡しも同様）。

## 書き方（最重要）

- **1文1情報**。短い文に分ける。
- 説明は**正確な操作記述を1文**。わかりやすさのための言い換えで曖昧さが出るなら正確な方を取る（例: `:h` は「親ディレクトリを返す」ではなく「末尾のパス名要素を取り除く」。ネスト時に何が返るか曖昧になるため）。
- 腹落ちは**実例（入力 → 出力）**が担当する。「何が返るか」は実例の `→` の右側が答える。「出力」は評価値に限らず、そのコードが生む具体物（解決されるファイルパス、発動するキー、作られるレコード等）でよい。
- コールバック/非同期APIは「**呼び出し自体が返す値**（多くは nil・即座に戻る）」と「**コールバックに渡る値**」を分けて書く。同期関数と誤読して戻り値を受けようとするのが定番の事故。
- コメントや文字列中の**他ファイル参照**（「Xの〜版」「Xを参照」）は、注釈でその正体を1行で解決する（何のファイルで、何が同じで何が違うか）。未解決の参照は読者の疑問として残る。
- **書かれなかった選択肢も書く**: 紛らわしい構文（クォート種別・類似演算子等）は隣接する書き方との対比で（「`'\t'` と `"\t"` は2文字のまま、タブになるのは `$'\t'` だけ」）、順序に意味がある早期return・ガードは「入れ替えたら何が壊れるか」を1行で書く。
- 多段パイプラインの `ex` は最終出力だけでなく中間状態（各段の出力・フィールド分解）も示す。
- 類推のダメ押し（「dirnameと同じ」等）・由来・うんちくは書かない。
- 構造が言葉より図で伝わるときだけ `fig`（小さな手書き風の図）を使う。1ファイルに0〜2個。
- **変数が暗黙に生まれる場所を明示する**: `read var`・コールバック引数・キャプチャなど、代入形でないのに変数が作られる箇所は「ここで `var` が作られる」と注釈する。読者の「この変数、急に出てきたけど何？」を潰す（`for var in` のような自明なものは除く）。
- **読者がデータを頭に描きながら読める状態を作る**: ループ・代入・分岐など、データが形を変える行には `trace`（その時点で変数に入っている実値の書き込み）を付ける。特にデータの出どころがその行より後ろにある構文（`while read` + `done < <(...)`、コールバック、遅延評価）では、ループ頭に「何が・何件・どこから」を必ず書き、出どころ行への `ref` を付ける。目安は1関数に3〜5個、データの形が変わらない行には付けない。

## 入口からの経路（言語・フレームワークに合わせる）

対象コードは単体では理解できない。「どこから呼ばれ、どう到達するか」を `entry` で必ず示す。形は生態系に合わせて選ぶ:

- **Rails等のサーバサイド**: ルーティング → コントローラ → 対象までの呼び出し経路（`stack`。各段に file:line）
- **React等のフロントエンド**: エントリ/ルーティングからのコンポーネント階層（`tree`。対象がどの階層で読み込まれるかを `here` で示す）
- **CLI・スクリプト**: 起動手段（task定義・alias・bin・cron）→ 対象（`stack`）
- **プラグイン・設定（Neovim等）**: 読み込み機構（require元・keymap・autocmd・イベント）→ 対象（`stack`）
- **ライブラリ/gem**: 利用者が呼ぶ公開API → 対象までの内部経路（`stack`）

経路は実物を辿って書く（routes.rb・エントリファイル・task定義を実際に読む。創作しない）。入口が複数あるなら主要なものだけ。

## 手順

1. 対象を読み、**実データを辿る**: 変数に実際に入る値を、リポジトリの実ファイル構成・schema・fixture・設定から特定する（創作しない）。不明なら安全なコマンドで確認する。パスは実行環境の配置（例: `~/.dotfiles/...`）で書く。
2. `<このスキルのdir>/template.html` の2つのプレースホルダを置換し、`~/annotations/YYYY-MM-DD-<slug>.html` へ書き出す（方法は任意: cp+Edit でも スクリプトでも。slug=対象ファイル名の拡張子をハイフン化: `link-sh`。ディレクトリがなければ作成）。**テンプレート内部の理解は不要**、置換だけでよい:
   - `__SRC__` → 対象コード全文をそのまま。注釈箇所だけ `⟦id⟧構文⟦⟧` で囲む。
     - id は `[A-Za-z0-9_-]` のみ。**閉じは id なしの `⟦⟧`**。エスケープは一切不要。
     - スパンは構文単位で最小に。ネスト不可（入れ子になったら外側を囲み、内側は別の出現箇所で囲むか外側カードで触れる）。
     - 変数名・引数が違っても同じ構文なら同じ id で、**全出現をマークする**（カードは初出の行に付き、2回目以降はカードへの誘導になる。実例は代表1つでよい）。
     - 対象が複数ファイルのときは各ファイルの先頭に `⟪path⟫` 行を置く（行番号はファイルごとにリセット）。
   - `__META__` → JSON:
     ```json
     {"title":"scripts/link.sh","lang":"zsh","summary":"1〜2文の要約",
      "entry":{"stack":[{"t":"mise run link","loc":"mise.toml:12"},{"t":"scripts/link.sh"}]},
      "flow":{"intro":"`zsh/.zshrc.d/alias.zsh` を1本追うと:",
              "steps":[{"t":"`zsh` はEXCLUDEにない → リンク対象","l":58}],
              "fig":{"rows":[["~/.zshrc.d/alias.zsh","リンク","~/.dotfiles/zsh/.zshrc.d/alias.zsh"]],
                     "caption":"任意"}},
      "issues":[{"line":57,"text":"実際に踏みうる問題だけ。無ければ空"}],
      "trace":[{"line":15,"text":"src = ~/.dotfiles/zsh/.zshrc など9件を1行ずつ。出どころ","ref":27}],
      "ann":{
       "id1":{"lv":1,"name":"構文名","what":"正確な1文（〜60字）","ex":"任意: 実例1行"},
       "id2":{"lv":2,"name":"構文名","syn":"一般形","what":"正確な操作記述1〜2文",
              "ex":"入力 → 出力 を実際の値で。\\n で複数行可",
              "ref":"任意: 公式リファレンスの該当セクションURL"}}}
     ```
     L1 で使えるキーは `name/what/ex` のみ。JSON内の `"` は `\"`。`entry`/`flow`/`issues`/`fig`/`ref` は任意（無ければキーごと省略）。複数ファイル時の行参照は `{"f":1,"l":44}` / `{"file":1,"line":44}`（省略時は最初のファイル）。
     `entry` は `stack`（縦の呼び出し経路: `[{"t":"表示名","loc":"file:line"},...]`）か `tree`（階層: ノードは `{"t":"名前","loc":"file:line","c":[子...],"here":true}`。`here`=対象コードの位置）のどちらかを持ち、`note` で補足1行を足せる。`title` で見出しを変えられる（既定:「入口 — どこから来るか」）。
3. **流れの整合チェック**: `flow` は代表例1本（対象に合う粒度: ファイル1本・リクエスト1回・コマンド実行1回・起動1回など）を実値で追い、各ステップに行参照 `l` を付ける。flow・issues に書いた用語や数字（例:「リンク切れを削除」「NGを数える」）は、**その答えになる注釈が該当行にあるか**セルフチェックする。読んで湧く疑問がその場で解消できなければ注釈を足す。trace に書いた意外な実値（並び順の逆転・件数・変換結果）も同様に、理由を担う注釈があるか確認し、その注釈の `ex` は**その結果を実際に決めた実データ**で書く（実在する別例で代用しない）。
4. 検証: `python3 <このスキルのdir>/check.py <出力html> <対象ファイル...>` — マーカーと ann の対応、原文との一致を機械チェック。NGなら直す。
5. 開く: `plannotator annotate <file>` をバックグラウンド実行（なければ `open`）。フィードバックが返ったら修正して再度開く。

## 品質基準

- `ex` は必ずこのリポジトリで実際に流れる値。机上の創作例は不可。
- `issues` は実際に踏みうる問題だけ（`set -e` を足したら壊れる、のような重箱ネタは書かない）。該当行の横に⚠カードとして出る。
- `ref` は公式リファレンスの該当セクションURL。**確信があるURLのみ**。うろ覚えなら公式ドキュメントのトップに落とす（捏造URLは信頼を壊す）。引用は不要、リンクだけでよい。
- 対象言語の仕様として正確であること。別言語・別シェルの挙動を混同しない（例: bashとzshのパイプライン挙動の違い）。
- 不慣れな言語の依頼では L2 を厚めに `ref` 付きで。慣れた言語では注釈を絞り、`flow` と `issues` を充実させる。不明なら両方。
