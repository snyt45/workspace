# Annotate

対象コードに手書き風注釈を付けた自己完結HTMLを生成する。全行解説ではなく、必要なところだけ書く。言語は問わない。
読者は経験のあるエンジニアで、AIが書いたコードや不慣れな言語を読む機会が多い。この構文は何で実際どんな値が入るのか、という質問を先回りして潰す。

## 手順

1. 対象を読み、実データを辿る。変数に実際に入る値をリポジトリの実ファイル構成やschema、fixture、設定から特定する（創作しない）。不明なら安全なコマンドで確認する。パスは実行環境の配置（例: `~/.dotfiles/...`）で書く。
2. `<このスキルのdir>/template.html` のプレースホルダを2つ置換し、`~/annotations/YYYY-MM-DD-<slug>.html` に書き出す。slugは対象ファイル名の拡張子をハイフン化（`link-sh`）。複数ファイルなら主対象ファイル名を使う（例: `csv-rb`）。ディレクトリがなければ作成する。テンプレート内部の理解は不要。置換だけで動く。
   - `__SRC__`: 対象コード全文。注釈箇所だけ `⟦id⟧構文⟦⟧` で囲む。
     - idは `[A-Za-z0-9_-]` のみ。閉じは id なしの `⟦⟧`。エスケープ不要。
     - スパンは構文単位で最小に。ネスト不可（入れ子になったら外側を囲み、内側は別の出現箇所で囲むか外側カードで触れる）。
     - 同じ構文は同じ id で全出現をマークする。カードは初出の行に付き、2回目以降はカードへの誘導になる。実例は代表1つでよい。
     - 対象が複数ファイルなら各ファイルの先頭に `⟪path⟫` 行を置く。行番号はファイルごとにリセット。
     - PR全体が対象なら diff のファイルを全件 `⟪path⟫` 区切りで含める。並び順は呼び出し経路順（入口側を先に）。左ツリーでファイルを開閉でき、viewed チェックで読み進めを管理できる。本題と無関係なファイルは載せない。
   - `__META__`: JSON。
     ```json
     {"title":"scripts/link.sh","lang":"zsh","summary":"1〜2文の要約",
      "entry":{"stack":[{"t":"mise run link","loc":"mise.toml:12"},{"t":"scripts/link.sh"}]},
      "flow":{"intro":"`zsh/.zshrc.d/alias.zsh` を1本追うと:",
              "steps":[{"t":"`zsh` はEXCLUDEにない → リンク対象","l":58}],
              "fig":{"rows":[["~/.zshrc.d/alias.zsh","リンク","~/.dotfiles/zsh/.zshrc.d/alias.zsh"]],
                     "caption":"任意"}},
      "issues":[{"line":57,"text":"実際に踏みうる問題だけ。無ければ空"}],
      "trace":[{"line":15,"text":"src = ~/.dotfiles/zsh/.zshrc など9件を1行ずつ。出どころ","ref":27}],
      "ann":{
       "id1":{"lv":1,"name":"構文名","what":"正確な1文（〜60字）","ex":"任意: 実例1行"},
       "id2":{"lv":2,"name":"構文名","syn":"一般形","what":"正確な操作記述1〜2文",
              "ex":"入力 → 出力 を実際の値で。\\n で複数行可",
              "ref":"任意: 公式リファレンスの該当セクションURL"}}}
     ```
     L1で使えるキーは `name/what/ex` のみ。JSON内の `"` は `\"`。`entry`/`flow`/`issues`/`fig`/`ref` は任意（無ければキーごと省略）。複数ファイル時の行参照は `{"f":1,"l":44}` / `{"file":1,"line":44}`（省略時は最初のファイル）。
     `entry` は `stack`（縦の呼び出し経路: `[{"t":"表示名","loc":"file:line"},...]`）か `tree`（階層: ノードは `{"t":"名前","loc":"file:line","c":[子...],"here":true}`。`here`=対象コードの位置）のどちらかを持ち、`note` で補足を足せる。note は「◯◯をすると」レベルの短文を改行区切りで並べる（1行1事実。詳述しない）。`title` で見出しを変えられる（既定: 呼び出し経路）。
3. 流れの整合チェック: `flow` は入口の呼び出しを受けた**実際のコード経路**を追う（spec の実行例でなく、実ファイルのメソッド遷移。実値はそのステップが触れるコード内の値）。各ステップに行参照 `l` を付ける。見出しは既定で「処理の流れ」。flow・issues に書いた用語や数字は、その答えになる注釈が該当行にあるか確認する。読んで湧く疑問がその場で解消できなければ注釈を足す。trace に書いた意外な実値も同様に理由を担う注釈があるか確認し、その注釈の `ex` はその結果を実際に決めた実データで書く。実在する別例で代用しない。
4. 検証: `python3 <このスキルのdir>/check.py <出力html> <対象ファイル...>` でマーカーと ann の対応、原文との一致を機械チェックする。NGなら直す。
5. 開く: `$plannotator-annotate` に委譲（フィードバックが返ったら修正して再度開く）。

## 品質基準

- `ex` は必ずこのリポジトリで実際に流れる値。机上の創作例は不可。
- `issues` は実際に踏みうる問題だけ。`set -e` を足したら壊れる、のような重箱ネタは書かない。該当行の横に⚠カードとして出る。
- 説明文は `$essence` に従う。what の1文目が結論、1文1情報。冗長・ノイズ（一般論・類推・うんちく・メタ説明）は排除し、事実だけを載せる。
- `ref` は公式リファレンスの該当セクションURLで、確信があるURLのみ。うろ覚えなら公式ドキュメントのトップに落とす。捏造URLは信頼を壊す。引用不要、リンクだけでよい。読者が次に調べたいであろう箇所には多めに付けてよい。
- 対象言語の仕様として正確であること。別言語や別シェルの挙動を混同しない（bashとzshのパイプライン挙動の違いなど）。
- 不慣れな言語の依頼では L2 を厚めに `ref` 付きで。慣れた言語では注釈を絞り、`flow` と `issues` を充実させる。不明なら両方。

## 書き方

各ルールは1つ選んで適用する。全部を一度に満たそうとしない。

- 1文1情報。短い文に分ける。
- 説明は正確な操作記述を1文で。わかりやすさのための言い換えで曖昧さが出るなら正確な方を取る。例: `:h` は「親ディレクトリを返す」ではなく「末尾のパス名要素を取り除く」。ネスト時に何が返るか曖昧になる。
- 腹落ちは実例（入力→出力）が担当する。何が返るかは実例の→の右側が答える。出力は評価値に限らず、そのコードが生む具体物（解決されるファイルパスや発動するキー、作られるレコード等）でよい。
- コールバックや非同期APIは、呼び出し自体が返す値（多くはnil、即座に戻る）とコールバックに渡る値を分けて書く。同期関数と誤読して戻り値を受けようとするのが定番の事故。
- コメントや文字列中の他ファイル参照は、注釈でその正体を1行で解決する。何のファイルで、何が同じで何が違うか。未解決の参照は読者の疑問として残る。
- 紛らわしい構文は隣接する書き方との対比で書く（`'\t'` と `"\t"` は2文字のまま、タブになるのは `$'\t'` だけ）。順序に意味がある早期returnやガードは、入れ替えたら何が壊れるかを1行で書く。
- 多段パイプラインの `ex` は最終出力だけでなく中間状態も示す。
- `ex` の実例には、それが代表する一般則を1句添える（例: `lhs=",?"` → lhs は `<leader>` 展開済みの実キーで返る）。例だけだと読者が帰納の責任を負う。文字クラス・パターン系の注釈は、このリポジトリの実データに当てた境界例（日本語や空白等の非ASCII挙動）を1つ含める。
- スコープ境界の依存を明示する。注釈対象ファイル群の外を指す識別子（コマンド名の文字列やグローバル変数、他ファイル定義のキーマップ等）は、定義元パスと不在時の失敗モードを⚠か既存カードの1文で書く。失敗モードが非対称なら（うるさく壊れる／静かにno-op／実行時エラー）その対比も書く。文字列結合の依存はコードから見えないため、注釈でしか補えない。
- 類推のダメ押し（dirnameと同じ等）や由来、うんちくは書かない。
- 構造が言葉より図で伝わるときだけ `fig`（小さな手書き風の図）を使う。1ファイルに0〜2個。
- 変数が暗黙に生まれる場所を明示する。`read var` やコールバック引数、キャプチャなど、代入形でないのに変数が作られる箇所は「ここで `var` が作られる」と注釈する（`for var in` のような自明なものは除く）。
- 読者がデータを頭に描きながら読める状態を作る。ループや代入、分岐などデータが形を変える行には `trace`（その時点で変数に入っている実値の書き込み）を付ける。特にデータの出どころがその行より後ろにある構文（`while read` + `done < <(...)`、コールバック、遅延評価）では、ループ頭に「何が・何件・どこから」を必ず書き、出どころ行への `ref` を付ける。目安は1関数に3〜5個。データの形が変わらない行には付けない。trace は青マークで表示され、ホバーで内容、クリックで出どころ行へ飛べる。

## 警告レベル

基準は「主流言語の汎用知識だけで意味を推測できるか」。対象言語固有でない構文（POSIX/bash共通、C系共通など）はレベルを下げる。迷ったら上に倒す。

- **L2 警告 🔴**: 構文を知らないと行の意味自体が推測できない、または見た目から想像する挙動と実際が乖離するもの。欄外カードに書く。
  例: zsh `${(s:/:)v}` `*(N/)`、Ruby `&:sym` `method_missing`、Railsの暗黙マジック、TS `infer` やmapped type、Terraform `[*]` や `dynamic`、JS `Proxy`
- **L1 注意 🟡**: 読めるが誤読や罠があるもの。ホバーで一言メモ。
  例: クォート有無で挙動が変わる、`-e` と `-L` の違い、JS `==`、Go `defer` の引数評価タイミング
- 汎用知識で読める行には何も付けない。目安: L2はユニーク構文数で5〜15個/100行（短いファイルは比例でよい）。
- 見た目は普通のコードだが実行環境に接続されている暗黙挙動（Neovimの `vim.g`、Railsのcallback等）もL2の対象。
- 構文でなく引数の意味が推測不能な場合も対象。外部APIに渡す裸の `true`/`false`/`nil`/数値フラグは、その引数が何を切り替えるかを一言注釈する。意味を持つ `nil` 渡しも同様。

## 入口からの経路（言語・フレームワークに合わせる）

対象コードは単体では理解できない。どこから呼ばれどう到達するかを `entry` で必ず示す。形は生態系に合わせて選ぶ。

- **Rails等のサーバサイド**: ルーティング→コントローラ→対象までの呼び出し経路（`stack`。各段に file:line）
- **React等のフロントエンド**: エントリやルーティングからのコンポーネント階層（`tree`。対象がどの階層で読み込まれるかを `here` で示す）
- **CLI・スクリプト**: 起動手段（task定義・alias・bin・cron）→対象（`stack`）
- **プラグイン・設定（Neovim等）**: 読み込み機構（require元・keymap・autocmd・イベント）→対象（`stack`）
- **ライブラリ/gem**: 利用者が呼ぶ公開API→対象までの内部経路（`stack`）

経路は実物を辿って書く（routes.rbやエントリファイル、task定義を実際に読む。創作しない）。入口が複数あるなら主要なものだけ。

## 削るセルフチェック（仕上げに必ず確認する）

注釈は多いほど良いのではない。読む量はオプトインでも、視界のノイズと冒頭ブロックの量は読者の体力を削る。以下を確認する。

- 各注釈が読者が実際に質問したはずのことに答えているか。答えていないものや他の注釈で自明になったものは削る。
- `flow` は5ステップ以内を目安。超えるなら代表例の粒度が大きすぎるサイン。分割するか要約する。
- 1画面（30行程度）に🔴カードや trace が4個以上並ぶ箇所は密度を疑う。🔴は1機能あたり8〜9枚を目安にし、そのカードの全事実が他の🔴＋相互参照1句で導出できるなら🟡へ降格する。導出できない同系カードは降格でなく1枚に統合する。
- 機能の核心主張は summary に1回だけ書く。entry の note や fig のキャプションで同じ文を再掲しない。
- fig は flow の箇条書きと同じ情報なら描かない。言葉で伝わらない構造だけ図にする。
- 外部APIの注釈は全引数の列挙をせず、この行の実引数での結果 ex 1行を優先する。
