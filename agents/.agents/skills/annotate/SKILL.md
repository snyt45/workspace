# Annotate

対象コードの「引っかかる構文」だけに注釈を付けた自己完結HTMLを生成する。全行解説ではない。言語は問わない。
読者は経験のあるエンジニア。ただしAIが書いたコードや不慣れな言語を読む機会が多く、「この構文は何で、何を返して、実際どんな値が入るのか」を毎回質問してきた人。その質問を先回りして潰すのが目的。

## 警告レベル

基準は「主流言語の汎用知識だけで意味を推測できるか」。対象言語固有でない構文（POSIX/bash共通、C系共通など）はレベルを下げる。迷ったら上に倒す。

- **L2 警告 🔴** — 構文を知らないと行の意味自体が推測できない、または見た目から想像する挙動と実際が乖離するもの。記号だらけでググりにくいものは特に。→ 欄外カード
  - 例: zsh `${(s:/:)v}` `*(N/)`、Ruby `&:sym` `method_missing`、Railsのcallback/scope等の暗黙マジック、TS `infer` やmapped type、Terraform `[*]` や `dynamic`、JS `Proxy` やタグ付きテンプレート
- **L1 注意 🟡** — 読めるが誤読・罠があるもの。→ ホバーで一言メモ
  - 例: クォート有無で挙動が変わる、`-e` と `-L` の違い、JS `==` の暗黙変換、Go `defer` の引数評価タイミング、Rubyの後置 `unless`
- 汎用知識で読める行には何も付けない。目安: L2はユニーク構文数で5〜15個/100行。超えたら平易なものを無印へ落とす。

## 手順

1. 対象ファイルを読み、**実データを辿る**: 変数に実際に入る値を、リポジトリの実ファイル構成・schema・fixture・設定から特定する（創作しない）。不明なら安全なコマンドで確認する。パスは実行環境の配置（例: `~/.dotfiles/...`）で書く。
2. `cp <このスキルのdir>/template.html ~/annotations/YYYY-MM-DD-<slug>.html`（slug=対象ファイル名の拡張子をハイフン化: `link-sh`。ディレクトリがなければ作成）
3. コピー先の2つのプレースホルダを置き換える（置換方法は任意。Edit でも sed でもよい）:
   - `__SRC__` → 対象コード全文をそのまま。注釈箇所だけ `⟦id⟧構文⟦⟧` で囲む。
     - id は `[A-Za-z0-9_-]` のみ。**閉じは id なしの `⟦⟧`**。エスケープは一切不要。
     - スパンは構文単位で最小に（行全体を囲まない）。
     - ネスト不可。入れ子になったら外側を囲み、内側は別の出現箇所で囲むか外側カードの `what`/`data` で触れる。
     - 変数名・引数が違っても同じ構文なら同じ id（カードは初出の行に付き、`data` は代表例1つでよい。2回目以降はクリックでカードへ飛ぶ）。
   - `__META__` → JSON:
     ```json
     {"title":"scripts/link.sh","lang":"zsh","summary":"1〜2文の要約",
      "flow":["全体が何をするかを3〜6ステップで"],
      "issues":[{"line":22,"text":"バグ疑い・罠・設計上の注意"}],
      "ann":{
       "id1":{"lv":1,"name":"構文名","what":"一言（〜60字）","data":"任意: 実値一例"},
       "id2":{"lv":2,"name":"構文名","syn":"一般形","what":"何をするか1〜2文",
              "ret":"評価結果の型・形","data":"入力 → 出力 を実際の値で。\\n で複数行可",
              "ref":"任意: 公式ドキュメントの該当セクションURL"}}}
     ```
     L1 で使えるキーは `name/what/data` のみ。JSON内の `"` は `\"`。`flow`/`issues` は任意。
4. 検証: `python3 <このスキルのdir>/check.py <出力html> <対象ファイル>` — マーカーと ann の対応、原文との一致を機械チェック。NGなら直す。
5. 開く: `plannotator annotate <file>` をバックグラウンド実行（なければ `open`）。フィードバックが返ったら修正して再度開く。

## 深さの調整

依頼者の対象言語への習熟度で配分を変える（不明なら両方入れる）:

- **不慣れな言語**（普段使わない・初見）: L2を厚めにし、各L2に `ref` を付けて構文を学びながら読めるようにする。`ref` は公式ドキュメントの該当セクションURL。**確信があるURLのみ**。うろ覚えなら言語公式ドキュメントのトップページに落とす（リンク切れ・捏造URLは信頼を壊す）。
- **慣れた言語**: 注釈は本当に引っかかる箇所だけに絞り、代わりに `flow`（全体の流れ）と `issues`（バグ疑い・罠・エッジケース。該当行番号付き）を充実させて「問題ないか」の判断まで支援する。`issues` は根拠のある指摘のみ。無ければ空でよい（無理に作らない）。

## 品質基準

- `data` は必ずこのリポジトリで実際に流れる値。机上の創作例は不可。
- L2カードだけ読めば追加質問が不要になる完結性。`what` は挙動、`ret` は評価後の形、`data` は実値、と役割を分ける。「なぜこの書き方か」に一言で答えられるなら `what` に含める。
- 対象言語の仕様として正確であること。別言語・別シェルの挙動を混同しない（例: bashとzshのパイプライン挙動の違い）。
