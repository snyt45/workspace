# サブエージェントへの委譲（herdr）

herdrの操作・構文・安全規則は herdr スキル（`herdr --skill`）に従う。このスキルは委譲の運用規約だけを定める。

## 階層は3択。ユーザーに確認して1つ選ぶ

| 階層 | 形 | 使う場面 |
|---|---|---|
| **lead単独** | lead が自分で作業（sub なし） | タスクが小さく、分割の利得がない |
| **2層** | lead → sub（複数可） | 通常。lead が1つの委譲元 |
| **3層** | 社長(chief) → lead（複数可） → sub | lead が2つ以上並ぶとき。エリア・プロジェクトの分割、複数 lead の統括 |

- 3層にするのは「lead が複数いて、誰が何をやるかの調整が必要なとき」だけ。強制しない
- 階層は後から変えられる（下記「昇格・降格」）。最初から3層に作り込まない

起動前に1メッセージの選択式でユーザーへ確認する:
1. **階層**（上記のどれか）
2. **エージェント数と構成**: 各エージェントのロール名・ハーネス（pi / claude）・使うモデル
   通常タスク（画像不要）はテキスト専用の安いモデルでよい。pi ハーネスのデフォルトは `deepseek-v4-flash`（$0.22/$0.66 per 1M）。claude ハーネスは `sonnet`（$2/$10・画像対応）。
   画像・スクリーンショットを読むタスクは低コストの画像対応モデル: `gpt-5.6-luna`（$0.2/$1.2・1M context）か `mimo-v2.5`（$0.14/$0.28）。テキスト専用モデルでは画像が読めない。
   重いタスク（原因究明・設計レビュー・難しい実装）は能力優先で引き上げる: pi は `kimi-k2.7-code`（$0.95/$4）、claude は `fable` / `opus`。
   画像対応可否は `input: ["text", "image"]` で判断。config は `~/.pi/agent/models-store.json` で確認する
3. **依頼内容**: 各エージェントに送るプロンプトの一行要約

複数エージェントでも全員分を1メッセージで確認する。承認を得てから起動する。

## 名前の規約（ロール名を付ける）

**lead は3層・2層共通の固定語。** 社長は chief と呼ぶ（agent 名は ASCII 制約 `[a-z][a-z0-9_-]{0,31}`）。

| ロール | agent 名の例 | pane ラベル（サイドバー表示） |
|---|---|---|
| 社長（chief） | `<project>-chief` | 社長 |
| lead | `<project>-lead` / `<project>-lead2` | lead（または担当名） |
| sub | 作業名（例: `spec-battle`・`code-core`） | 作業名 |

付け方（どちらも実在するコマンド）:
- `herdr agent rename <pane-id> <name>` — agent 名。これは以後の `agent prompt` の宛先になる
- `herdr pane rename <pane-id> <label>` — サイドバーに表示されるラベル。日本語にできる（社長 など）

名前は herdr セッション全体（全workspace横断）で一意。`agent_name_taken` になったらプロジェクト名や連番を付けて回避する。
下の起動・昇格の手順で、agent 名と pane ラベルの両方を付けること（名前が pane に付かない、という状態を作らない）。

## 起動手順

配置は固定で **1オーケストラ=1タブ、呼び出し元workspace内**。

1. **自分（委譲元）にロール名を付ける**: `herdr agent rename "$HERDR_PANE_ID" <role>`（例: `<project>-chief` か `<project>-lead`）+ `herdr pane rename "$HERDR_PANE_ID" <ラベル>`
2. 新規タブ作成 → ルートpaneを分割 → 各paneに `agent start`（ロール名、`--timeout 60000`）→ 依頼プロンプト送信

   タブ作成:
   ```
   herdr tab create --workspace "$HERDR_WORKSPACE_ID" --label <タスク名> --cwd <プロジェクト>
   ```
   `--workspace` を省略すると UI でフォーカス中の workspace（別プロジェクトのことが多い）に作られる。作成応答の `tab.workspace_id` が `$HERDR_WORKSPACE_ID` と一致することを確認する。不一致なら閉じて作り直す。

   分割の配置指針: 横に広いpaneは right、縦に狭いpaneは down。同じ方向の連続分割で細くしすぎない。先に right で2列にしてから各列を down で割ると見やすい。
3. 各paneにロール名と同じラベルを付け、`agent start`（ロール名、`--timeout 60000`）→ 依頼プロンプト送信

## 3層（社長→lead→sub）の組み方

### ボトムアップ（よくある形: 後から社長になる）

1. はじめは lead として作業（2層で起動。名前は `<project>-lead`）
2. 別の lead が既に動いている・これから必要になる、と分かったら**社長に昇格**する:
   - `herdr agent rename "$HERDR_PANE_ID" <project>-chief` ＋ `herdr pane rename "$HERDR_PANE_ID" 社長`
   - 既存 lead に1通だけ通知する: 「これからの完了報告の宛先を <project>-chief に変えてください。起動中の作業はそのまま続けてください」＋新しい定型句（下記）
   - これで既存 lead が「読み込まれた」状態になる。再起動は不要
3. lead の報告は chief が回収し、判断を返す。lead 同士の調整も chief が1人で受ける（lead どうしが直接連絡しない）

### トップダウン（最初から3層）

chief を起動したら、各 lead に「あなたの担当範囲と報告先（chief名）」だけを渡して起動する。lead が sub を持つなら、leader 自身が orchestrate スキルを読み、sub を起動する。

### 降格（chief → lead）

3層が必要なくなったら、chief の pane を `agent rename --clear` で戻し、lead へ「報告先を元の lead 名へ戻す」通知を1通送る。pane は閉じない（後でまた使える）。

## 依頼プロンプトの定型句

末尾に必ず付ける。宛先は「報告先ロール」:
- 2層: 報告先 = lead（自分）
- 3層: sub → lead に報告。lead は回収・取りまとめ後、同じ定型句で chief へ報告（**段階報告**）

```
完了したら、この pane のシェルで以下を実行してから終了してください:
herdr agent prompt <報告先名> "完了報告: <変更/調査の要約・検証結果・懸念点>"
（報告文に引用符は含めない。長文は一時ファイルに書いて、そのパスを送ってください）
```

指示の出し手が誰でも、サブエージェントにはこの定型句を入れる。報告は1段上のロールへ送らせる（lead が把握・回収・報告できるように）。chief は lead からしか直接受けない。

## コンテキスト最小化の原則（重要）

**委譲できる読み・書き・検証はすべて委譲する。chief と lead は自分で全部読まない。**

- **chief**: リポジトリを直接読むのは「判断に必要な1ファイル」だけ。読み・調査・読み返しは lead に委譲し、chief は「要約・コミットハッシュ・議決が必要な点」だけを受けて判断する
- **lead**: 作業範囲全体を読まない。タスクに必要なファイルだけを読む（必要最低限のコンテキスト）
- **依頼プロンプトに本文や資料を貼らない**。参照先（ファイルパス・commit range・PR 番号・仕様の節）と、ゴール・完了条件・制約だけを書く。足りなければ lead が自分で読む
- **報告は要約のみ**。長文は一時ファイルに書いてパスを渡させる（既存ルール）
- 判断が要る点だけを chief/lead へ上げさせ、判断済みのことは上げさせない

## 回収（プッシュ方式）

```
   chief(pi) ──▶ lead ──▶ sub（依頼）
     ▲            │ 要約      │ 完了
     │            ▼           │
     └── agent prompt chief ◀── lead（sub の報告を取りまとめて chief へ）
```

- 委譲元は prompt 後ブロックせず、自分の作業を続けてよい。完了報告は `herdr agent prompt` 経由で pi の入力として届き、自動でターンが再開する
- 報告が届いたら `agent read <名前>`（ファイルパスがあればそれも確認）で最終出力を確認し、要約をユーザーへ報告する。届いたターンで必ず完了させる
- 複数を並走させた場合は、届いた順に処理する。特定の1体を待ち続けない
- 報告への返信はユーザーにのみ。サブエージェントへ自動返信しない（無限ループになる）。追加指示はユーザー確認後に既存エージェントへ `agent prompt` する

## フォールバック（報告が来ないとき）

サブエージェントがクラッシュした・定型句を守らなかった等で報告が届かない場合は pull で回収する:

- `agent list` で全体状態を確認しながら、`wait`（`--timeout 60000` 程度で刻み）→ `read` で完了した順に回収して報告する
- `blocked`（承認・質問待ち）は read で状況を確認して解消する。放置しない

## その他の運用ルール

- 同一リポジトリへ並列書き込みする場合は、起動前に worktree を分ける（または編集ファイルを直行させ、衝突を避ける）
- 回収・報告後も pane・タブは閉じずに残す（続きの指示や確認に使える）。同じロールへの追加依頼は新規起動せず既存エージェントを再利用する
- 閉じるのは、不要になったことをユーザーに確認してから。自分が作った pane・タブだけを閉じる
- タイムアウト後も起動していることがあるので pane を確認し、生きていれば rename して続行する
