# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。レビュー基準は本人の過去レビュー指示から抽出したもの。

## レビュー原則

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除。最初の実装は最小限。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。
3. **コメントよりコード** — コメントで補足が要る時点で、命名か設計を疑う。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造の明瞭さ・依存の向き・テスト容易性・予測可能性・変更容易性。

## 報告しないもの（全軸共通）

- **失敗シナリオが書けない指摘** — 呼び出し元を追い、「どんな入力・状況で、誰がどう困るか」を具体的に1つ書けなければ破棄する
- 今回の変更が導入していない既存の問題（変更がそれを悪化させる場合を除く）
- 抑制コメント（`rubocop:disable` / `eslint-disable` 等）付きのコード — 著者の意図的決定として尊重する
- リンタが捕まえるもの・主観的な好み

## 手順

### 1. 固定点を決めて差分を取る

ユーザー指定の固定点（SHA・ブランチ・タグ等）を使う。指定がなければ `origin/main` を既定とし、その旨を伝える。

- `git rev-parse <fixed-point>` で解決を確認し、`git diff <fixed-point>...HEAD`（3ドット）と `git log <fixed-point>..HEAD --oneline` を取得する。
- 差分が空ならここで終了する。サブエージェントの中で失敗させない。

### 2. 些細な差分は軽量パスで見る

typo修正・rename・1〜2行の変更・生成ファイルのみ、といった些細な差分なら5体は起動しない。lead が直接差分を読み、上の原則で確認して報告する。報告には軽量パスで見たことを明記する。

### 3. 仕様ソースを特定する

spec-scope-check に渡す仕様を次の順で探す:

1. コミットメッセージの issue 参照（`#123` 等）→ `gh issue view` / `gh pr view` で取得
2. ユーザーが引数で渡したパスや依頼文
3. 見つからなければユーザーに一言確認する。仕様がなければ spec-scope-check はスコープ観点のみで実行する

### 4. スタック別基準を選ぶ

差分の拡張子を見て、該当する基準ファイルを読み込む（複数該当可）:

- `.rb` を含む → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` を含む → [references/frontend.md](references/frontend.md)

### 5. サブエージェント5体を並列起動

起動手段は環境依存。**herdr が使える環境では herdr pane で5体を並列起動する**（本スキルの既定）。ネイティブの Agent ツールが露出している環境ではそちらでもよい。

#### 5a. 起動手段の判定（起動前に必ず確認）

```bash
test "${HERDR_ENV:-}" = 1 && which herdr
```

- 成功 → 5b の herdr pane 方式
- 失敗 → 5c のフォールバック（lead が5つの役割を自分で1パス実行）

#### 5b. herdr pane で5体を並列起動（推奨・既定）

1. **5ペイン作成**: 現在の pane から右/下に交互 split（`herdr pane split --current --direction right|down --cwd "$PWD" --no-focus`）。戻り値 JSON の `.result.pane.pane_id` を読む。同じ方向の連続 split で細すぎるペインを作らない
2. **エージェント起動**: `herdr agent start <名前> --kind pi --pane <id>`。名前は `[a-z][a-z0-9_-]{0,31}` で、役割名を使う（responsibility / naming / test-quality / critical-impact / spec-scope）。`agent start` はエージェントが入力受付になるまで待つ
3. **プロンプト送信（並列）**: `herdr agent prompt <名前> "<本文>" --wait --timeout 300000`。5体は独立ペインなのでそのまま並列で動く。**エージェントはこのスキルを読めない**ため、本文に必ず含める: ①役割定義（agents/*.md の全文） ②該当するスタック別基準（references/*.md）の全文 ③diffコマンドとコミット一覧 ④仕様（あれば spec-scope-check のみ）⑤出力フォーマット指示。プロンプトは実行後に返事を求める形で書く
4. **回収と後片付け**: `herdr agent read <名前> --source recent-unwrapped --lines 200` で出力を回収 → `herdr pane close <pane-id>` で閉じる

起動する5体:

- [responsibility-check](agents/responsibility-check.md) — 責務・設計品質
- [naming-comment-check](agents/naming-comment-check.md) — 命名・コメント
- [test-quality-check](agents/test-quality-check.md) — テスト価値・カバレッジ
- [critical-impact-check](agents/critical-impact-check.md) — クリティカル・顧客影響
- [spec-scope-check](agents/spec-scope-check.md) — 仕様・スコープ

担当境界: 名前の実態・統一・マジックストリングは naming-comment の専任で、responsibility は名前に踏み込まない。投機的実装を削る判断は spec-scope の専任で、responsibility は要件から来た拡張だけを見る。

エージェント定義の共通部（報告しないもの・出力フォーマット・テスト方針）は各定義に自己完結で書いてある。文言を変えるときは `agents/` 以下の全該当箇所を同時に修正する。

#### 5c. フォールバック（herdr が無い環境）

lead が5つの役割チェックリストを自分で順に1パス実行し、各指摘に役割タグを付けて手順6のフォーマットで集約する。報告冒頭に「フォールバック（サブエージェント未起動）」と明記する。並列レビューの代替であり、指摘の質は保つ。

> ⚠️ 退行防止: 手順5を「Agent ツールの呼び出し」前提に書き換えないこと。pi のデフォルト環境にはネイティブ Agent ツールが露出しない場合があり、その場合 herdr pane（5b）が唯一の並列起動手段。ツールに Agent 呼び出しが無くても 5b は実行できる。

### 6. 集約

役割ごとの見出しで全指摘を列挙しない。**冒頭の結論 + 重大度3層**で報告する。軸をまたいだ再ランクはしない — 各エージェントの重大度判定をそのまま層に振り分ける。

**冒頭3行の結論**:

```
結論: マージ前に直すべき 2件 / 削除候補 4件 / 任意（好み） 3件
判定: ⚠️ 修正してからマージ
理由: （1行）
```

3層の構成:

- **層1: マージ前に潰す（最大5件）** — critical-impact の致命・高 + 他軸の「高」のみ。
- **層2: 削除候補リスト** — 全軸から「消せるもの」（デッドコード・冗長コメント・過剰オプション・価値のないテスト・要求外の変更）だけを集約。最重要基準が「削る」ため、この層は必ず置く。
- **層3: 任意（好みの範疇）** — 件数と1行要約だけ。「詳細が要るなら聞いて」で締める。

書式ルール:

- 1指摘1行: `file:line — 問題の要約 → 直し方 [軸タグ/重大度]`。エージェントの詳細フォーマットは集約時に1行へ圧縮する。
- 層1の指摘には失敗シナリオと影響範囲を添える（例: 「この関数は12箇所から呼ばれる」）。この層だけは2行になってよい。
- 同一指摘が複数軸から出たら1件に統合し、軸タグを併記する（例: `[責務][命名] file:line — …`）。重複排除であり再ランクではない。
- 指摘ゼロの軸は「問題なし」と明言し、1行に畳む（例: 「問題なし: 命名 / テスト / 仕様」）。各エージェントの総評文は転記しない。

**検証パス**: 層1に載せる前に、lead が該当コードと呼び出し元を読み、失敗シナリオが実際に成立するかを確認する。成立しなければ載せない。誤検出は、読者が判断できない報告を生む最大の要因。
