# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。

レビュー基準は本人の過去のレビュー指示から抽出した総合原則:

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除。最初の実装は最小限。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。複雑化したら戻してでも設計をやり直す。
3. **コメントよりコード** — よく考え抜かれたコード >>> コメント。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。「毎回微妙に違う」を許さない。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造が一目で分かるか、依存の向きは正しいか（依存性の逆転）、テストしやすい境界か、予測可能で変更しやすいか。
7. **報告しないもの**（全軸共通）— 確信が持てない指摘・リンタが捕まえるもの・主観的改善提案・特定入力に依存する理論上の問題（実害の再現経路が示せないもの）は報告しない。

## 手順

### 1. 固定点を決める

ユーザーが指定した固定点（SHA・ブランチ・タグ等）を使う。指定がなければ `origin/main` を既定とし、その旨を伝える。

- `git rev-parse <fixed-point>` で解決を確認し、`git diff <fixed-point>...HEAD`（3ドット）と `git log <fixed-point>..HEAD --oneline` を取得する。
- 差分が空ならここで終了する。サブエージェントの中で失敗させない。

### 2. 仕様ソースを特定する

spec-scope-check に渡す仕様を次の順で探す:

1. コミットメッセージの issue 参照（`#123` 等）→ `gh issue view` / `gh pr view` で取得
2. ユーザーが引数で渡したパスや依頼文
3. 見つからなければユーザーに一言確認。「ない」なら spec-scope-check はスコープ観点のみで実行

### 3. スタック別基準を選ぶ

差分の拡張子を見て、該当する基準ファイルを読み込む（複数該当可）:

- `.rb` を含む → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` を含む → [references/frontend.md](references/frontend.md)

### 4. サブエージェント5体を並列起動

1つのメッセージで5つの Agent 呼び出しを送る。各エージェントには **diffコマンド・コミット一覧・該当するスタック別基準の全文・対応する観点ファイルの全文** を含める（サブエージェントはこのスキルを読めない）。仕様がある場合、spec-scope-check には仕様全文も渡す:

- [responsibility-check](agents/responsibility-check.md) — 責務・設計品質
- [naming-comment-check](agents/naming-comment-check.md) — 命名・コメント
- [test-quality-check](agents/test-quality-check.md) — テスト価値・カバレッジ
- [critical-impact-check](agents/critical-impact-check.md) — クリティカル・顧客影響
- [spec-scope-check](agents/spec-scope-check.md) — 仕様・スコープ

担当境界: 名前（実態・統一・マジックストリング）は naming-comment が専任（responsibility は名前に踏み込まない）。投機的実装の削除判断（YAGNI）は spec-scope が専任（responsibility は要件から来た拡張だけを見る）。他軸が同対象に触れたら指摘を1件に統合し、軸タグを併記する。

**エージェント定義の共通部**（「無理に指摘をひねり出さない」・出力フォーマット・テスト方針等）はサブエージェントがスキルを読めないため各定義に自己完結で書く。文言を変えるときは `agents/` 以下の全該当箇所を同時に修正する。

### 5. 集約

役割ごとの見出しで全指摘を列挙するのはやめ、**重大度3層 + 冒頭の結論**で報告する。軸をまたいだ再ランクはしない — 各エージェントの重大度判定をそのまま層に振り分けるだけ（どの視点の指摘かは軸タグ `[責務]` 等で保存する）。

**冒頭3行の結論**（結論ファースト。読者が途中で離れても判断できるように）:

```
結論: マージ前に直すべき 2件 / 削除候補 4件 / 任意（好み） 3件
判定: ⚠️ 修正してからマージ
理由: （1行）
```

**層1: マージ前に潰す（最大5件）** — critical-impact の致命・高 + 他軸の「高」のみ。1指摘1行:

```
- file:line — 問題の要約 → 直し方 [軸タグ/重大度]
```

**層2: 削除候補リスト** — 全エージェントの指摘から「消せるもの」（デッドコード・冗長コメント・過剩オプション・価値のないテスト・要求外の変更）だけを1行ずつ集約する。ユーザーの最重要基準が「削る」ため、この層は必ず置く。

**層3: 任意（好みの範疇）** — 件数と1行要約だけ。「詳細が要るなら聞いて」で締める。

各層の指摘は **1件1行**（場所 — 問題 → 直し方）。エージェントの詳細フォーマット（場所/観点/問題/提案/重大度の5項目縦書き）は集約時に1行へ圧縮する。

**「問題なし」の軸は1行に畳む**（例: 「問題なし: 命名 / テスト / 仕様」）。各エージェントの総評文は転記しない。

**同一指摘が複数軸から出たら1件に統合**し、軸タグを併記する（例: `[責務][命名] file:line — …`）。重複排除であり再ランクではない。

**検証パス**: 層1に入る致命・高の指摘は、報告前に lead が該当コードを読んで「本当にそうか」を確認してから載せる。誤検出の報告が「判断できない報告」の最大要因。

指摘ゼロの軸は「問題なし」と明言する。無理に指摘をひねり出さない。
