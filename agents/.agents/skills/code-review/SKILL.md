# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。レビュー基準は本人の過去レビュー指示から抽出したもの。

## レビュー原則

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除。最初の実装は最小限。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。
3. **コメントよりコード** — コメントで補足が要る時点で、命名か設計を疑う。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造の明瞭さ・依存の向き・テスト容易性・予測可能性・変更容易性。

## 報告しないもの（全軸共通）

- **失敗シナリオが書けない指摘** — 呼び出し元を追い、「どんな入力・状況で、誰がどう困るか」を具体的に1つ書けなければ破棄する
- 今回の変更が導入していない既存の問題（変更がそれを悪化させる場合を除く）
- 抑制コメント（`rubocop:disable` / `eslint-disable` 等）付きのコード — 著者の意図的決定として尊重する
- リンタが捕まえるもの・主観的な好み

## 手順

### 1. 固定点を決めて差分を取る

ユーザー指定の固定点（SHA・ブランチ・タグ等）を使う。指定がなければ `origin/main` を既定とし、その旨を伝える。

- `git rev-parse <fixed-point>` で解決を確認し、`git diff <fixed-point>...HEAD`（3ドット）と `git log <fixed-point>..HEAD --oneline` を取得する。
- 差分が空ならここで終了する。サブエージェントの中で失敗させない。

### 2. 些細な差分は軽量パスで見る

typo修正・rename・1〜2行の変更・生成ファイルのみ、といった些細な差分なら5体は起動しない。lead が直接差分を読み、上の原則で確認して報告する。報告には軽量パスで見たことを明記する。plannotator review へのコメント注入（手順6）は省略してよい。

### 3. 仕様ソースを特定する

spec-scope-check に渡す仕様を次の順で探す:

1. コミットメッセージの issue 参照（`#123` 等）→ `gh issue view` / `gh pr view` で取得
2. ユーザーが引数で渡したパスや依頼文
3. 見つからなければユーザーに一言確認する。仕様がなければ spec-scope-check はスコープ観点のみで実行する

### 4. スタック別基準を選ぶ

差分の拡張子を見て、該当する基準ファイルを読み込む（複数該当可）:

- `.rb` を含む → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` を含む → [references/frontend.md](references/frontend.md)

### 5. サブエージェント5体を並列起動

起動の仕組み（新規タブ・pane分割・`agent start`・prompt・回収）は `$orchestrate` に従う。**1オーケストラ=1タブ**で、5体をタブ内のpaneに1体ずつ起動する。

各エージェントのプロンプトには必ず含める（サブエージェントはこのスキルを読めない）:

1. 役割定義の全文 — [agents/](agents/) の対応ファイル
2. スタック別基準の全文 — 手順4で選んだ [references/](references/) のファイル
3. diffコマンドとコミット一覧
4. 仕様全文（あれば。spec-scope-check のみ）
5. 完了報告の定型句（`$orchestrate` に記載）

起動する5体:

- [responsibility-check](agents/responsibility-check.md) — 責務・設計品質
- [naming-comment-check](agents/naming-comment-check.md) — 命名・コメント
- [test-quality-check](agents/test-quality-check.md) — テスト価値・カバレッジ
- [critical-impact-check](agents/critical-impact-check.md) — クリティカル・顧客影響
- [spec-scope-check](agents/spec-scope-check.md) — 仕様・スコープ

担当境界: 名前の実態・統一・マジックストリングは naming-comment の専任で、responsibility は名前に踏み込まない。投機的実装を削る判断は spec-scope の専任で、responsibility は要件から来た拡張だけを見る。

エージェント定義の共通部（報告しないもの・出力フォーマット・テスト方針）は各定義に自己完結で書いてある。文言を変えるときは `agents/` 以下の全該当箇所を同時に修正する。

herdr が使えない環境では lead が5つの役割を自分で1パス実行し、各指摘に役割タグを付けて手順6のフォーマットで集約する。報告冒頭に「フォールバック（サブエージェント未起動）」と明記する。

### 6. 集約

報告は**軸ごと**に行う。書き方は `$essence` に従う（結論ファースト・文ごとに改行・冗長排除・同じ情報を2箇所に置かない）。軸をまたいだ再ランクはしない — 各エージェントの重大度判定をそのまま使う。

**冒頭3行の結論**:

```
結論: マージ前に直すべき 2件 / 削除候補 2件 / 好み 11件
判定: ⚠️ 修正してからマージ（指摘ゼロなら ✅ そのままマージ可）
理由: （1行。マージ可否を左右する判断根拠だけ）
```

**軸ごとのセクション**（並び順: クリティカル・影響 → 責務・設計 → テスト → 命名・コメント → 仕様・スコープ）:

- 見出し: `## 軸名（N件）`。
- 指摘は軸内で重大度の高い順に並べる。各指摘は `### [重大度] file:line — タイトル` で始め、本文は文ごとに改行する（1指摘3〜6行）。
- 本文の構成: 問題（何がどう困る）→ 失敗シナリオ・影響範囲（マージ前修正対象は必須）→ 直し方（1行）。
- 消せる指摘には `[削除候補]` タグを付ける（デッドコード・冗長コメント・過剰オプション・価値のないテスト・要求外の変更）。最重要基準が「削る」ため、削除候補は必ず結論の件数に含める。
- 指摘ゼロの軸は末尾に `問題なし: 軸名` と1行で畳む。各エージェントの総評文は転記しない。

書式ルール:

- 1行に2文以上詰めない。改行で読むリズムを作る。
- 同一指摘が複数軸から出たら1件に統合し、タグに両軸を併記する（例: `[影響][命名]`）。配置は主軸のセクション。重複排除であり再ランクではない。
- 軸ごとの重大度語彙は各軸のものをそのまま使う（クリティカルは致命/高/中/低、責務・命名・仕様は高/中/低、テストは弱いテスト/カバレッジの穴）。

**検証パス**: マージ前修正対象に載せる前に、lead が該当コードと呼び出し元を読み、失敗シナリオが実際に成立するかを確認する。成立しなければ載せない。誤検出は、読者が判断できない報告を生む最大の要因。

**修正案の作成**: 検証パス中に、マージ前修正対象の指摘へ最小の before/after コードを書く。他指摘の修正と矛盾しないこと、現実的であることを確認する。

**plannotator review へのコメント注入**: 集約した指摘を `plannotator review` の実差分にインラインコメントとして注入し、ブラウザで開く（手順は [references/review-report.md](references/review-report.md)）。軽量パス（手順2）では省略してよい。フィードバックが返ったら集約に反映する。
