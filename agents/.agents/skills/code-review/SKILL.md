# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。

## レビュー原則

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除する。最初の実装は最小限。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。
3. **コメントよりコード** — コメントで補足が要る時点で、命名か設計を疑う。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造の明瞭さ・依存の向き・テスト容易性・予測可能性・変更容易性。

## 報告しないもの（全軸共通）

各エージェント定義の「報告しないもの」に従う。共通ルールは1つ: **失敗シナリオが書けない指摘は報告しない**（呼び出し元を追い、「どんな入力・状況で誰がどう困るか」を1つ書けなければ破棄する）。

## 手順

### 1. 固定点を決めて差分を取る

ユーザー指定がなければ `origin/main` を既定とする。

- `git diff <fixed-point>...HEAD`（3ドット）と `git log <fixed-point>..HEAD --oneline` を取得する。
- 差分が空なら終了する。

### 2. 些細な差分は軽量パスで見る

typo修正・rename・1〜2行の変更・生成ファイルのみなら5体は起動しない。lead が直接差分を読み、上の原則で確認して報告する。plannotator注入（手順6）は省略してよい。

### 3. 仕様ソースを特定する

1. コミットメッセージの issue 参照（`#123` 等）→ `gh issue view` / `gh pr view` で取得する。
2. ユーザーが引数で渡したパスや依頼文。
3. 見つからなければユーザーに確認する。なければ spec-scope-check はスコープ観点のみで実行する。

### 4. スタック別基準を選ぶ

拡張子で判定する（複数該当可）:

- `.rb` → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` → [references/frontend.md](references/frontend.md)

### 5. サブエージェント5体を並列起動

`$orchestrate` に従い、1タブ内のpaneに5体を1体ずつ起動する。

各エージェントのプロンプトには以下を含める（サブエージェントはこのスキルを読めない）:

1. 役割定義の全文 — [agents/](agents/) の対応ファイル
2. スタック別基準の全文 — 手順4で選んだファイル
3. diffコマンドとコミット一覧
4. 仕様全文（あれば。spec-scope-check のみ）
5. 完了報告の定型句（`$orchestrate` に記載）

起動する5体:

| エージェント | 役割 |
|---|---|
| [responsibility-check](agents/responsibility-check.md) | 責務・設計品質 |
| [naming-comment-check](agents/naming-comment-check.md) | 命名・コメント |
| [test-quality-check](agents/test-quality-check.md) | テスト価値・カバレッジ |
| [critical-impact-check](agents/critical-impact-check.md) | クリティカル・顧客影響 |
| [spec-scope-check](agents/spec-scope-check.md) | 仕様・スコープ |

担当境界: 命名の実態・統一・マジックストリングは naming-comment の専任。投機的実装を削る判断は spec-scope の専任。herdr が使えない環境では lead が5役割を1パスで実行し、各指摘に役割タグを付けて手順6のフォーマットで集約する（報告冒頭に「フォールバック」と明記する）。

### 6. 集約する

書き方は `$essence` に従う（結論ファースト・文ごとに改行・冗長排除・同じ情報を2箇所に置かない）。軸をまたいだ再ランクはしない。

**冒頭3行の結論**:

```
結論: マージ前に直すべき 2件 / 削除候補 2件 / 好み 11件
判定: ⚠️ 修正してからマージ（指摘ゼロなら ✅ そのままマージ可）
理由: （1行。マージ可否を左右する判断根拠だけ）
```

**軸ごとのセクション**（並び順: クリティカル・影響 → 責務・設計 → テスト → 命名・コメント → 仕様・スコープ）:

- 見出し: `## 軸名（N件）`。
- 指摘は軸内で重大度の高い順に並べる。各指摘は `### [重大度] file:line — タイトル` で始め、本文は文ごとに改行する（1指摘3〜6行）。
- 本文の構成: 問題（何がどう困る）→ 失敗シナリオ・影響範囲（マージ前修正対象は必須）→ 直し方（1行）。
- 消せる指摘には `[削除候補]` タグを付ける。削除候補は結論の件数に含める。
- 指摘ゼロの軸は末尾に `問題なし: 軸名` と1行で畳む（総評文は転記しない）。

書式ルール:

- 同一指摘が複数軸から出たら1件に統合し、タグに両軸を併記する（例: `[影響][命名]`）。配置は主軸のセクション。
- 軸ごとの重大度語彙は各軸のものをそのまま使う（クリティカルは致命/高/中/低、責務・命名・仕様は高/中/低、テストは弱いテスト/カバレッジの穴）。

**検証と修正案**: マージ前修正対象は、lead が該当コードと呼び出し元を読み、失敗シナリオが成立するか確認してから載せる。同時に before/after コードを書く。他指摘の修正と矛盾しないこと。

**plannotator review への注入**: 集約した指摘を `plannotator review` の実差分にインラインコメントとして注入する（手順は [references/review-report.md](references/review-report.md)）。軽量パス（手順2）では省略してよい。フィードバックが返ったら集約に反映する。
