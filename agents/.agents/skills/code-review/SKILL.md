# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。

レビュー基準は本人の過去のレビュー指示（toypo-api / フロント系 / dotfiles のログ採掘）から抽出したもの。総合原則:

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除。最初の実装は最小限。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。複雑化したら戻してでも設計をやり直す。
3. **コメントよりコード** — よく考え抜かれたコード >>> コメント。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。「毎回微妙に違う」を許さない。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。

## 手順

### 1. 固定点を決める

ユーザーが指定した固定点（SHA・ブランチ・タグ等）を使う。指定がなければ `origin/main` を既定とし、その旨を伝える。

- `git rev-parse <fixed-point>` で解決を確認し、`git diff <fixed-point>...HEAD`（3ドット）と `git log <fixed-point>..HEAD --oneline` を取得する。
- 差分が空ならここで終了する。サブエージェントの中で失敗させない。

### 2. 仕様ソースを特定する

spec-scope-check に渡す仕様を次の順で探す:

1. コミットメッセージの issue 参照（`#123` 等）→ `gh issue view` / `gh pr view` で取得
2. ユーザーが引数で渡したパスや依頼文
3. 見つからなければユーザーに一言確認。「ない」なら spec-scope-check はスコープ観点のみで実行

### 3. スタック別基準を選ぶ

差分の拡張子を見て、該当する基準ファイルを読み込む（複数該当可）:

- `.rb` を含む → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` を含む → [references/frontend.md](references/frontend.md)

### 4. サブエージェント5体を並列起動

1つのメッセージで5つの Agent 呼び出しを送る。各エージェントには **diffコマンド・コミット一覧・該当するスタック別基準の全文** を含める（サブエージェントはこのスキルを読めない）:

| エージェント | 役割 |
|---|---|
| `responsibility-check` | 責務の配置・単一責任・複雑さ・既存実装との一貫性 |
| `naming-comment-check` | 命名の実態一致・周辺との統一・コメント過多・マジックストリング |
| `test-quality-check` | テストの価値（トートロジー/モック過多）とカバレッジの穴。テスト方針: 実装をなぞる細かいロジックテストより、通しで動くことを担保するブラックボックスE2Eを優先（it 1つでも可） |
| `critical-impact-check` | クリティカルな問題・エッジケース・顧客影響（データ損失・権限・金銭・セキュリティ・後方互換性の破壊・例外時の一貫性・境界値・部分失敗・既存ユーザーへの振る舞い変更）。様式美でなく実害の有無が基準 |
| `spec-scope-check` | 仕様との一致・scope creep・要求外の変更（仕様があれば仕様全文も渡す） |

### 5. 集約

役割ごとの見出しで報告する。**軸をまたいだ再ランクはしない** — ある軸の合格が別の軸の問題を隠すのを防ぐため。

**「クリティカル/顧客影響」は実害の観点なので、critical-impact-check の致命・高は削除候補ではなく冒頭の「マージ前に潰すべきもの」として別枠で先に提示する。**

最後に必ず **「削除候補リスト」** を置く: 全エージェントの指摘から「消せるもの」（デッドコード・冗長コメント・過剩オプション・価値のないテスト・要求外の変更）だけを1行ずつ集約する。ユーザーの最重要基準が「削る」ため。

指摘ゼロの軸は「問題なし」と明言する。無理に指摘をひねり出さない。
