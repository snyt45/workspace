# Code Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューする。

## レビュー原則

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除する。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。
3. **コメントよりコード** — コメントで補足が要る時点で、命名か設計を疑う。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造の明瞭さ・依存の向き・テスト容易性・予測可能性・変更容易性。

## 報告ルール

報告しないものは各エージェント定義に従う。共通ルールは1つ: **失敗シナリオが書けない指摘は報告しない**。

## 手順

### 1. 固定点を決めて差分を取る

ユーザー指定がなければ `origin/main` を既定とする。

- `git diff <fixed-point>...HEAD`（3ドット）とコミット一覧を取得する。
- 差分が空なら終了する。

### 2. 軽量パス

条件: typo修正・rename・1〜2行の変更・生成ファイルのみ。

手順: lead が直接差分を読み、レビュー原則で確認して報告する。plannotator注入（手順6）は省略する。

### 3. 仕様ソースを特定する

以下の順で探す:

1. コミットメッセージの issue 参照 → `gh issue view` / `gh pr view` で取得する。
2. ユーザーの引数や依頼文。
3. 見つからなければユーザーに確認する。なければ spec-scope-check はスコープ観点のみで実行する。

### 4. スタック別基準を選ぶ

拡張子で判定する（複数該当可）:

- `.rb` → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` → [references/frontend.md](references/frontend.md)

### 5. サブエージェント5体を並列起動

`$orchestrate` に従い、1タブ内のpaneに5体を1体ずつ起動する。

各エージェントのプロンプトに含める内容:

1. 役割定義の全文 — [agents/](agents/) の対応ファイル
2. スタック別基準の全文 — 手順4で選んだファイル
3. diffコマンドとコミット一覧
4. 仕様全文（あれば。spec-scope-check のみ）
5. 完了報告の定型句（`$orchestrate` に記載）

起動する5体:

| エージェント | 役割 |
|---|---|
| [responsibility-check](agents/responsibility-check.md) | 責務・設計品質 |
| [naming-comment-check](agents/naming-comment-check.md) | 命名・コメント |
| [test-quality-check](agents/test-quality-check.md) | テスト価値・カバレッジ |
| [critical-impact-check](agents/critical-impact-check.md) | クリティカル・顧客影響 |
| [spec-scope-check](agents/spec-scope-check.md) | 仕様・スコープ |

担当境界:

| エージェント | 他軸と干渉しない範囲 |
|---|---|
| naming-comment | 命名の実態・統一・マジックストリングは専任。responsibility は名称に踏み込まない。 |
| spec-scope | 投機的実装を削る判断は専任。responsibility は要件から来た拡張だけを見る。 |
| responsibility | 上記2軸の判断に委ねられた領域には踏み込まない。 |

**フォールバック**: herdr が使えない環境では、lead が5役割を1パスで実行する。
各指摘に役割タグを付け、手順6のフォーマットで集約する。
報告冒頭に「フォールバック」と明記する。

### 6. 集約する

書き方は `$essence` に従う。軸をまたいだ再ランクはしない。

**冒頭3行の結論**:

```
結論: マージ前に直すべき 2件 / 削除候補 2件 / 好み 11件
判定: ⚠️ 修正してからマージ（指摘ゼロなら ✅ そのままマージ可）
理由: （1行。マージ可否を左右する判断根拠だけ）
```

**軸ごとのセクション**: 並び順はクリティカル・影響 → 責務・設計 → テスト → 命名・コメント → 仕様・スコープ。

- 見出し: `## 軸名（N件）`
- 指摘は軸内で重大度の高い順。各指摘は `### [重大度] file:line — タイトル`
- 本文は問題→失敗シナリオ・影響範囲（マージ前修正対象は必須）→ 直し方。文ごとに改行（1指摘3〜6行）
- 削除候補は `[削除候補]` タグを付け、結論の件数に含める
- 指摘ゼロの軸は `問題なし: 軸名` と1行で畳む（総評文は転記しない）

**書式ルール**:

- 同一指摘が複数軸から出たら1件に統合し、タグに両軸を併記する（例: `[影響][命名]`）。配置は主軸のセクション。
- 軸ごとの重大度語彙をそのまま使う（クリティカル: 致命/高/中/低、責務・命名・仕様: 高/中/低、テスト: 弱いテスト/カバレッジの穴）。

**検証と修正案**: マージ前修正対象は、lead が該当コードと呼び出し元を読み、失敗シナリオが成立するか確認してから載せる。
同時に before/after コードを書く。

**plannotator注入**: 集約した指摘を `plannotator review` の実差分にインラインコメントとして注入する（手順は [references/review-report.md](references/review-report.md)）。
軽量パスでは省略する。
フィードバックが返ったら集約に反映する。
