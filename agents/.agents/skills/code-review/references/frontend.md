# フロントエンド (TypeScript / React) の基準

本人の過去レビュー指示（toypo-app / toypo4store-web / toypo-lma-builder）から抽出。

- **view はバカであれ**: view は加工済みデータを表示するだけ。ロジック・分岐・整形は view hook へ。宣言的に「見える」ことまで含めて要求水準。
- **神 hook / 神コンポーネント禁止**: reload も create も update も1つの hook でやらない。hook のための単一責任 hook があってよい。
- **依存の向き**: 親が自身の持たない値を子に渡していたら設計ミスのサイン。context で import して values に流し込めるものを view から流し込まない。「本当にここまでフロントが知っておくべきこと？」を問う。
- **命名**: 実態と一致（couponCode 特化なのに汎用名等は NG）。`pool !== null` より `isOpen` のような意味のある状態名。UI 文言はエンドユーザーに通じる語彙か（「在庫プールって一般的？」）。
- **型は手書きせず導出する**: `as` で書くより元の型から `Pick`。`keyof typeof` を再定義するより元の箇所で export して import。元の型変更に追従できる形を選ぶ。
- **マジックストリング排除**: エンドポイントパス等はファイル内定数に。フォーマット文字列等の知識は共通化されていないか先に探す。
- **既存の流儀**: 定数は strings.ts の流儀（キャメルケース等）に合わせる。styled より css 等、リポジトリの最新の書き方を確認してから書く。UI は既存画面（参考実装）に揃える。
- **セキュリティは allowlist 型**: 許可タグを列挙して外は escape。deny リスト型のパターンマッチは NG。ただし脅威モデルは現実的に（事業者しか触らない入力への過剰防御は不要）。
- **リリース順序の安全性**: API より先にフロントがリリースされても壊れないかを確認する。
