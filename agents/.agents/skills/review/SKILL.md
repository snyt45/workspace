# Review

固定点から `HEAD` までの差分を、役割別のサブエージェント5体で並列レビューし、確定した指摘を届ける。

## 3つの原則

1. **正確性は交渉の余地がない。** 指摘が「本当に問題か」を断言する前に、該当コードと呼び出し元を読んで確認する。ライブラリ仕様・API挙動に不安があれば `web_search` / `fetch_content` で調べる。**未確認の誤り指摘（誤検知）はレビューの信頼を壊す** — 自信満々の幻覚より、確認した上での少数の指摘が勝る。
2. **各指摘に影響と直し方が伴う。** 「ダメ」だけで終わらせない。何が起きるか（影響）と、どう直すか（具体的な変更）を書く。書き方は `$review-comment`。
3. **言葉より図が勝るときだけ図を使う。** 変更の構造（依存・呼び出し・フロー）が文章より図で伝わる場合のみ、`visualize` / `call-diagram` を使う。迷ったら省略 — ない図は偽の図より安い。

## レビュー原則

1. **とにかく削る** — 不要コード・過剰オプション・デッドコード・価値のないテストは削除する。
2. **シンプルさ最優先** — 初見で理解できない複雑さは受け入れない。
3. **コメントよりコード** — コメントで補足が要る時点で、命名か設計を疑う。
4. **既存との一貫性** — 新規コードは周辺の構成・命名・パターンに揃える。
5. **責務の置き場** — 知りすぎているクラス・賢すぎる呼び出し側・神hookを許さない。
6. **設計品質** — データ構造の明瞭さ・依存の向き・テスト容易性・予測可能性・変更容易性。

## 指摘の書き方

`~/.agents/skills/review-comment/SKILL.md` を読んで従う。重大度・破棄基準・書式はすべてそちらが持つ。

報告しないものは各エージェント定義に従う。

## 手順

### 1. 固定点を決めて差分を取る

ユーザー指定がなければ `origin/main` を既定とする。

- `git diff <fixed-point>...HEAD`（3ドット）とコミット一覧を取得する。
- 差分が空なら終了する。

### 2. 軽量パス

条件: typo修正・rename・1〜2行の変更・生成ファイルのみ。

手順: lead が直接差分を読み、レビュー原則で確認してチャットで報告する。指摘カードの出力は不要。

### 3. 仕様ソースを特定する

以下の順で探す:

1. コミットメッセージの issue 参照 → `gh issue view` / `gh pr view` で取得する。
2. ユーザーの引数や依頼文。
3. 見つからなければユーザーに確認する。なければ spec-scope-check はスコープ観点のみで実行する。

### 4. スタック別基準を選ぶ

拡張子で判定する（複数該当可）:

- `.rb` → [references/ruby.md](references/ruby.md)
- `.ts` / `.tsx` → [references/frontend.md](references/frontend.md)

### 5. サブエージェント5体を並列起動（herdr）

**`test "${HERDR_ENV:-}" = 1` が通るなら必ずherdrで起動する。** ハーネス内蔵の並列サブエージェント機能（Claude CodeのAgent tool等）は使わない — ユーザーが各paneでレビューの進行を見られることが要件。

`$orchestrate` に従い、1タブ内のpaneに5体を1体ずつ起動する（`herdr agent start <ロール名> --kind <pi|claude> --pane <pane-id>`）。
プロンプト送信の失敗と起動未達を見逃さないこと。全員の実行開始を確認してから待機に入る。

**依頼プロンプトは短く、本文はファイル参照で渡す**（長文のCLI送信は壊れる。`$orchestrate` のコンテキスト最小化原則）:

1. 役割定義: `~/.agents/skills/review/agents/<エージェント名>.md` を読んで従うよう指示する（全文を貼らない）
2. スタック別基準: 手順4で選んだファイルのパス（`~/.agents/skills/review/references/...`）
3. diffコマンドとコミット一覧の取得コマンド（出力は貼らない）
4. 仕様（あれば。spec-scope-check のみ）: 一時ファイルに書いてパスを渡す
5. 指摘の検証指示: 各指摘は該当コードと呼び出し元を読んで成立を確認し、未確認のまま挙げない（付随させる）
6. 完了報告の定型句（`$orchestrate` に記載）。指摘一覧は一時ファイルに書かせ、報告にはパスと件数だけ入れさせる

起動する5体:

| エージェント | 役割 |
|---|---|
| [responsibility-check](agents/responsibility-check.md) | 責務・設計品質。命名の指摘と投機的実装の判定は該当軸に譲る。 |
| [naming-comment-check](agents/naming-comment-check.md) | 命名・コメント（実態・統一・マジックストリング） |
| [test-quality-check](agents/test-quality-check.md) | テスト価値・カバレッジ |
| [critical-impact-check](agents/critical-impact-check.md) | クリティカル・顧客影響 |
| [spec-scope-check](agents/spec-scope-check.md) | 仕様・スコープ（投機的実装の削除判定含む） |

**フォールバック**: `HERDR_ENV` が無い環境でのみ、lead が5役割を1パスで実行する。各指摘に役割タグを付けて手順6に進む。どう実行したか（herdr の有無・体制）は報告に書かない。

### 6. 集約して出力する

**検証**: マージ前修正対象は、lead が該当コードと呼び出し元を読み、失敗シナリオが成立するか確認してから載せる。同一指摘が複数軸から出たら1件に統合する。

**出力形式**（結論 → 指摘カードの順）:

#### 結論（3行以内。書き方は `$essence`）

```
結論: マージ前に直すべき 2件 / 削除候補 2件 / 好み 11件
判定: ⚠️ 修正してからマージ（指摘ゼロなら ✅ そのままマージ可）
理由: （1行。マージ可否を左右する判断根拠だけ）
```

指摘ゼロならここで終了。

#### 指摘カード（1指摘 = 1カード）

`$review-comment` の型（結論→影響→直し方）で書く。並び順はクリティカル・影響 → 責務・設計 → テスト → 命名・コメント → 仕様・スコープ、軸内は重大度の高い順。

```markdown
### [軸][重大度] タイトル
`file:line` — 結論（1行）

影響: （何が起きるか）
直し方: （具体的な変更）
```

確認が必要で確定できない指摘は、カードに「要確認」と明記して疑いとして提示する（未確認のまま断定しない）。

#### 貼り先が指定されたとき

PR コメント・Slack など貼り先を指定されたら、指摘カードの列挙ではなく、そのまま貼れる本文を1ブロックで出す。結論1文 → 何が起きるか → 修正後の全体像の順。レビューの過程と体制は落とす。

#### 図（必要なときだけ）

変更の全体像や呼び出し関係を文章で説明するより図が勝る場合のみ、`visualize` スキルに図を委譲して1枚添える。迷ったら省略（散文や1行の方が勝るなら使わない）。
