# Review Comment

指摘1件の書き方だけを決める。何を探すか（観点）と、どこに出すか（walkthrough / plannotator / チャット / PR）は呼び出し側が決める。

読み手は経緯を知らない実装者。自分ではない誰かが、このコメントだけを見て直せることがゴール。

## 型

```
結論（1文）

影響（1行ずつ・箇条書き）

直し方（before/after）
```

## 書かないもの

- **追跡の過程** — 「A は B を呼び、B の戻り値は C なので」。結論だけ書く。疑うなら本人がコードを読む
- **再現手順** — 影響の記述から逆算できる。条件が結論に含まれないときだけ1行足す
- **言い直し** — 同じことを別の言葉で繰り返さない
- **前置き** — 「〜を確認しました」「良い実装ですが」

目安は300字。超えてよいのは before/after のコードを載せるときだけ。

## 正直に見積もる

- **既存の問題か、この変更で生まれたか**を必ず区別する。既存なら「既存の問題だが、今回この経路が増える」と書く
- **自己修復するものは重大度を下げる**。バッチが1時間で直す・一覧から消えるなら、そう書いて下げる
- **呼び出し元を実際に読んでから書く**。戻り値を無視している・例外を握りつぶしている・エラーメッセージが捨てられている、は読まないと分からない
- 確認していないことは書かない。書くなら未確認と明示する

調べた結果が実害小なら、重大度を下げるか取り下げる。取り下げる判断も仕事のうち。

## 直し方を書く

**before/after を出す。** 提案が別ファイル・別行にまたがるなら、その行番号を書いてコードブロックで示す。

出す前に確認する:

- **繋がるか** — scope をチェーンするなら、リレーションの型・テーブル別名・ポリモーフィックかどうかまで見る
- **副作用** — 影響範囲が広がる（serializer にも効く）・確率が変わる（重みが再配分される）・戻り値の型が変わる（Relation → Array）
- **別の問題を生まないか** — 生むなら反対意見として書く。「候補から外すと、選んだものが黙って無視されて成功が返る」

## 判断を仰ぐ

仕様の判断はこちらで決めない。事実だけ並べて問いにする。

```
利用済みかつ期限切れが 409 から 400 に変わります。意図した変更でしょうか。
```

## 同型の指摘は畳む

同じ原因の指摘が3箇所以上に散っていたら、個別に並べず**方針の指摘1件**に畳む。各所には結論と直し方だけを残す。

方針コメントに書くこと:

- 根本原因（1〜2文）
- 守るべきルール（2〜3個）
- 共通の受け皿になるコード

## 重大度

| | 基準 |
|---|---|
| 致命 | データ損失・金銭・セキュリティ・広範囲の顧客影響 |
| 高 | 特定条件で顕在化する障害。500・データ不整合・誤った通知 |
| 中 | まれな条件下・影響限定・自己修復する |
| 低 | 実被害が小さい・様式の問題 |

**失敗シナリオが書けない指摘は出さない。** 「どんな入力・状況で、誰がどう困るか」を示せないものは破棄する。指摘ゼロは正当。

## サブエージェントの中間報告

lead に渡す段階はこの形でよい（最終形は lead が上の型に整える）:

- **場所**: `file:line`
- **観点**: 担当軸の観点のどれか
- **問題 / 失敗シナリオ**: 誰がどう困るか
- **提案**: 直し方（方向性でよい）
- **重大度**: 上表
