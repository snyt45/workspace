# 設計比較ディスカッション（system-design-discuss）

複数の設計案を比較して、関係者と共通認識を取れる HTML 資料を生成する。
`template.html`（同じディレクトリ）に従う。

## フェーズ1: インタビュー

推奨回答を添えて1問ずつ、事実は自分で調べる。
**共通理解が得られるまで実装・生成を始めない。**

**ユーザーの発言は仮の要件。そのまま信用しない。** 特に「〜は不要」「〜はスコープ外」という発言は、フェーズ2で実物と矛盾しないか確認してから確定する。

1. **本題** — 何を解決したいか。1文で。
2. **スコープ外** — 何を扱わないか。
3. **案の定義** — 比較する各案をユーザーの理解と一致させる。ここがズレると資料全体が無駄になる。
4. **制約** — 触れられないもの・他への影響。

## フェーズ2: 検証

各案の前提を**実コードで検証**する。
想定と実態のズレをここで潰す。

**検証対象はコードだけでなく、ユーザーの要件・前提も含む。** ズレたら実物を優先し、ユーザーに確認する。要件の明確化は検証と生成の過程でも続く。

- 各案が依存するもの（外部インターフェース等）の**実在**とデータ形状（実装を読んで確認する）
- 型・スキーマの二重管理（同じ概念の型が2つある等）
- 設定値・分岐条件（ハードコードされた値等）
- 影響範囲（利用箇所・既存テスト）
- 工数は**実測ベース**（既存類似実装の行数・spec 数を調べる。見積もりを書くときは根拠を添える）
- 既存バグ・負債（新実装が既存のバグをコピーしうる場所）
- 必要なら `$orchestrate` で独立視点（Backend / Frontend 等）を並列レビューして検証結果を突き合わせる

## フェーズ3: HTML 生成

`template.html` は骨組み。内容は「設計比較資料に必ず載せる内容」に従う。

1. `<トピック>-design-review.html` として保存する
2. `$html-quality` でレビューし、指摘を修正する
3. フェーズ4（Plannotator）へ進む

## フェーズ4: フィードバック（Plannotator）

`$plannotator-annotate` に委譲して開く。注釈が返ってきたら反映して再度開く。
注釈が来なくなったら完了。

---

## 設計比較資料に必ず載せる内容

文章・情報設計は `$essence` に任せる。ここでは「設計比較というジャンルの内容要件」を定める。**これは最低限。** 判断に効く情報（影響範囲・利用マップ・変更前後の対比等）は要件に無くても載せる。`$essence` のノイズ排除が落とすのは判断に効かない情報であり、判断に効く情報を削ることではない。

1. 結論（何を選ぶべきか）
2. 各案の1行サマリー
3. 比較表（工数・リスク・負債・リクエスト数等）
4. 背景（本題・現状・制約・スコープ外）
5. 各案の詳細（実装ポイント + メリット/デメリット）
6. 図解（構造の違い・データフロー。Mermaid や UML 等の標準図法で描く）
7. 先に決めるべき論点

**実装ポイントは「現状 → 変更後」の対比で示す**（diff 形式 or 両方）。変更後のみだと、読者は変更前が分からず評価できない。

**影響範囲・利用マップは設計比較の核心情報**。変更が既存のどこに触れるか（どの画面・feature・クライアントが依存しているか）を図か表で示す。これが無いと、読者は「どの程度のリスクか」を判断できない。
