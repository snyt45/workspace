# 設計比較ディスカッション（system-design-discuss）

複数の設計案（例: 既存 API 組み合わせ vs 新エンドポイント）を比較して、関係者と共通認識を取れる HTML 資料を生成する。対応する `template.html`（同じディレクトリ）に従う。

## フェーズ1: インタビュー（grilling 連携）

起動したら、以下の項目を**1問ずつ**詰める（grilling スキルの流儀: 推奨回答を添えて、1問ずつ、事実は自分で調べる）。**共通理解が得られるまで実装・生成を始めない。**

1. **本題** — 何を解決したいか。1文で。（例: 「ホームのクーポン一覧デザインが変わり、現状の API では必要な情報が返せない」）
2. **スコープ外** — 何を扱わないか。（例: 「パフォーマンスは二の次」）
3. **案の定義** — 比較する各案をユーザーの理解と一致させる。ここがズレると資料全体が無駄になる。（例: 案B は「connections_controller を Fork して新エンドポイント」であり「新規 god endpoint のゼロ設計」ではない）
4. **制約** — 触れられないもの・他への影響。（例: 「他クライアントが使ってるので Backend のレスポンスは変えられない」）

注意: このフェーズで「本題」と「スコープ外」を確定しないと、資料が二流になる（今回の事例: パフォーマンスが副次なのにメイン扱いになった）。

## フェーズ2: 検証

各案の前提を**実コードで検証**する。想定と実態のズレをここで潰す。

- 各案が使うエンドポイントの**実在**とレスポンス形状（controller / serializer を読む）
- 型・スキーマの二重管理（同じ概念の型が2つある等）
- バージョン分岐・設定値（例: `Toypo-App-Version` ヘッダのハードコード）
- 影響範囲（他クライアント・他 feature・既存テスト）
- 工数は**実測ベース**（既存類似実装の行数・spec 数を調べる。見積もりを書くときは根拠を添える）
- 既存バグ・負債（今回の事例: `Connection#preview_coupon_contents` の引数順逆転）
- 必要なら orchestrate スキルで独立視点（Backend / Frontend 等）を並列レビューして検証結果を突き合わせる

## フェーズ3: HTML 生成

`template.html` は**最小の骨組み**（結論 → 比較サマリー → 背景 → 各案 → 図解 → 論点）にすぎない。**品質基準（下記）を満たす限り、スタイル・レイアウト・表現は自由に改善してよい。** テンプレートに固定しないこと。モデルや時代が変われば、より良い構成・デザインが生まれる余地を残す。

生成後は **html-quality スキル**（チェックリスト A〜H）でレビューしてから出力する。

出力先: 作業ディレクトリに `<トピック>-design-review.html` のような名前で保存する。

## フェーズ4: フィードバック（Plannotator）

`plannotator annotate <生成したHTML>` で開き、注釈が返ってきたら反映して再起動する（`pkill -f "plannotator annotate"` → 再起動）。注釈が来なくなったら完了。

## 品質基準（このスキルの核心）

出力前に以下を**全て**満たすこと。どれか1つ欠けたら修正する。

### 1. 自己完結性（初見で読める）

- 会話で使った用語・前提（固有名詞、バージョン、アプリ名）は HTML 冒頭で定義する。会話にしかない前提を本文で使わない
- 「前述」「§x 参照」のような内部参照を**書かない**。必要ならその場で一言説明する
- 各セクションが単独で読めて、前後を読まなくても意味が通る

### 2. 情報量の制御（詰め込みすぎない）

- 順序は**結論 → 1行サマリー → 比較表 → 詳細**。最初の画面（結論 + 比較表）だけで判断できるようにする
- **推奨/非推奨の理由は必ず比較サマリーに置く**（比較の文脈で見せる）。各案の詳細セクションには置かない。今回の事例: 案B の非推奨理由（二重保守・connection 2系統・工数）は比較表の直後の verdict にまとめるべきで、詳細セクションの見出し直後に置くのは読者が「なぜ？」を先に見たい場所とズレる
- 詳細（コード・論点）は後半に置くか `<details>` で折りたたむ
- 1セクションにコードは**最大1つ**、note（補足）は**最大1つ**
- メリット/デメリットは各**5個まで**（重要度順）
- 表の行も10行を目安に絞る

### 3. 図解

- データフロー・案の構造差は**図で**（SVG / Mermaid / テキスト図）。「文章で読むより図が早い」ものは必ず図にする
- 図は本文の後に置き、図だけで構造が分かるようにラベルを付ける

### 4. 箇条書き・表

- 長文はリスト化する。比較は表にする（表 + 1行の補足、で足りるなら文章は書かない）

### 5. 一貫性

- 用語の統一（案A / 案B の呼び名、エンドポイントの書き方）
- 結論と各セクションの記述が矛盾していないか（今回の事例: 「limit を足せば解決」と「connections は軽くならない」が矛盾した）
- 出力前に「初見の人が読んでわかるか」をシミュレーションする

### 6. ノイズの排除

- **関係者の判断に影響しない情報を載せない**。今回の事例: 案B（POST /connections を Fork）の説明に、LMA が使っていない別の god endpoint（GET /api/v2/home 等）の話を載せた。LMA に関係ない事実は、たとえ Backend 的に正しくてもノイズ。
- 「この案の評価に効くか？」でフィルタする。Backend 全体の話ではなく、今回の選択肢の話だけを載せる
