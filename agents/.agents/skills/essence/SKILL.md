# 文章・情報設計の本質（essence）

ユーザーが繰り返した品質指摘から抽出した、文章・情報設計の個人基準。  
良い文書・読みやすい文章・図・ドキュメントのすべてに通じる。

## 原則

### 構成（どこに・何を・どの順番で）

1. **本題と副次を分ける**
   - 最初に「何が本題か・何を扱わないか」を確定
   - 副次をメイン扱いしない。載せる場合も副次と明記して、本題と混ぜない

2. **結論ファースト**
   - 最初に結論。理由はその後。読者が途中で離れても判断できる順序
   - 判断理由（推奨/非推奨・採用/不採用の根拠）はサマリーに集約し、詳細に散らばらせない

3. **情報設計を徹底する**
   - 各情報ブロックについて「どこに・何を・どの順番で・どの形式で」を考える
   - 形式の使い分け: 比較→表 / 理由→箇条書き / 背景→短い文章 / 構造→図 / コード→コードブロック
   - 配置は「読者が次に知りたいこと」で決める。前後の文脈を無視した貼り付けをしない
   - 同じ情報を複数箇所に置かない（置き場所は1箇所。再掲は分散・矛盾の温床）

4. **詰め込みすぎない**
   - 情報が詰まりすぎると、人は理解しづらく、AIは重要でない情報に引っ張られて誤った方向へ進む。過剰な情報量の弊害は、読者もモデルも同じ
   - 1画面・1セクションで伝えるメッセージは1つ
   - 詳細は折りたたむ・後半に置く。読者が最初に必要なのは判断材料
   - リストは5個まで。超えたら重要度で分割する（今やる/後で等）。ランク付きの5個は無序の10個に勝る

### 文（どう書くか）

5. **冗長を排除する**
   - 説明のための説明を書かない（「〜に注意」「〜の余地を残す」「〜が重要だ」のようなメタ説明は、言わなくても分かるなら削る）
   - 一文は一つのこと。2つ以上のことを言ったら分割
   - 同じことを別の言葉で繰り返さない。同義語の言い換え連打もやめて1回で言い切る
   - 前置き宣言（「結論から言うと」「本記事では」）や締めの定型句（「参考になれば幸いです」）を入れない

6. **初見で読める**
   - 会話コンテキストを本文に含めない。前提（固有名詞・バージョン）は本文中で自己完結に定義
   - 内部参照（前述・§x 参照）を避け、必要ならその場で一言

7. **抽象語で押し切らない**
   - 「重要」「効果的」「最適」「本質」などの抽象語だけで押さない。動詞中心の具体表現にする

8. **文のリズムと記号**
   - 文のリズムを均一にしない。短い文と長い文を混ぜる。接続詞は最小限
   - 文を連ねて1行・1段落に詰めない。文ごとに改行し、読むリズムを作る
   - 強調の「」・()・コロン・スラッシュ並列・矢印（→）を多用しない。補足は本文の一文に組み込む
   - 一人称を出すなら一貫させる（「私／筆者／私たち」を混ぜない）

### 内容（何を載せるか）

9. **事実ベースで書く**
   - 捏造しない。元の文章にない数字・固有名詞・事例は足さない
   - 「一般的に」「多くの場合」「状況によって異なります」などの安全クッションは削除
   - 曖昧な箇所は曖昧なまま（読みやすく整えるだけ）

10. **ノイズを排除する**
    - 読者の判断に影響しない情報は載せない（事実として正しくても）
    - 「この情報は読者の判断を変えるか？」でフィルタする
    - スコープ外の話題は載せない（他のスキル・文書の領分に踏み込まない）

11. **一貫性を保つ**
    - 用語を統一する（同じものを同じ呼び方で）
    - 結論と本文の記述を矛盾させない
    - 数値・工数・日付を別の意味で使い回さない
    - 部分修正したら冒頭から通読する（局所の加筆は話の飛び・情報量の急変・文脈の断絶を生む。全体の流れとリズムが保たれているかを毎回確認する）

### 指示文書を書くとき

12. **具体例に引きずられない**
    - 原則・本質は抽象化して書く。固有名詞・技術スタック固有の実例（API 名・変数名・バグ名・プロジェクト名・特定フレームワークの構成要素等）をスキルや指示に埋め込まない
    - 具体例が必要なら最小限に。その場限りの例でなく、どの文脈でも通じる形にする
    - 設計資料・解説文書には適用しない（そこでは固有名詞・正確な名前が必須）。対象はスキル・プロンプト・指示文書のみ

13. **モデルに任せる**
    - 原則だけ示し、表現・構成・デザインはモデルの裁量に委ねる
    - 「必ず〜しなさい」を減らす。原則が守られていれば自由
    - 固定化は品質向上の機会を殺す。テンプレートは骨組みまで

## 使い方

- 文章・資料・HTML・スキルを書くとき: 生成後に原則 1〜13 を確認
- レビューするとき: 原則を適用して修正候補を出す
- 他のスキル（`$system-design-discuss`, `$html-quality` 等）の文章・情報設計部分は、この原則に従って書く・直す

## フィードバックループ

このスキルはユーザーの指摘から常に更新される。

### 反映手順（指摘が出たらその都度）

1. ユーザーが文章・情報設計について指摘したら、指摘を**原則の言葉に翻訳**する
2. **その場で原則へ反映する**:
   - 既存原則の言い換えで済む → 原則の文言を更新
   - 新しい原則 → 原則を追加（増える前に既存への統合を検討）
   - 矛盾・重複 → 統合
3. 反映後、`feedback.md` は「## 反映待ち（なし）」のテンプレに戻す

### 運用ルール

- 他スキル経由（HTML 生成・レビュー等）で出た文章・情報設計の指摘も、単独起動時と同じく反映対象にする
- feedback.md は一時バッファ。指摘を書き留めたら、**このセッション内で反映して空にする**
- 反映できない指摘（文脈が不明・判断が要る）は feedback.md に残し、次回の反映対象にする
- 文言変更の履歴は残さない（原則自体が最新の本質。経緯は git に任せる）
