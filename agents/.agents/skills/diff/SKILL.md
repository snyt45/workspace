# Diff

差分を上から順に辿り、変更の流れを理解できる形で解説する。レビュー（審査）ではなく、理解が目的。

## 3つの原則

1. **正確性は交渉の余地がない。** コードの挙動・ライブラリ仕様・関数の意味に不安があれば、推測を書く前に確認する。確認手段: 実コードを読む、`web_search` / `fetch_content` で仕様を調べる、重い調査は researcher サブエージェントに委譲する。**未確認のまま断言しない**。説明に誤りが1つあると、その後のステップすべてへの信頼が壊れる。
2. **各ステップに動機がある。** 単に「何が変わったか」ではなく「**なぜこの変更が必要なのか**」を語る。根拠はコミットメッセージ・PR説明・実装から取る。動機なしの変更は恣意的に見え、読者は定着しない。
3. **読みやすさは形式で作る。** 長文のステップ列で書かない。結論1行 → ASCII図 → 1行ステップの順で出し、散文は図・表に載らない補足だけに残す。図は自前のASCII（呼出図方式）を基本とし、`visualize` への委譲は描画が必要なときだけ。

## 手順

### 1. 差分を取る

- PR番号/URLが指定されたら: `gh pr diff <PR>` と `gh pr view <PR>`（説明・コミット一覧）
- 指定がなければ: `git diff origin/main...HEAD`（3ドット）とコミット一覧
- 差分が空なら終了する

### 2. 理解を固める（正確性の検証）

説明を書き始める前に、変更の本質を正確に掴む:

- 変更がどの層（API / サービス / UI / DB）に及ぶか、何を達成する変更かを掴む
- 新しいライブラリ・API・パターンが登場したら、その挙動を確認する（実コード・ドキュメント・web検索）。知らない関数の意味を憶測で書かない
- 変更の意図がコミットメッセージ・PR説明から読み取れない場合は、該当コードと呼び出し元を読んで確認する。それでも不明なら推測ではなく確認事項として明示する

### 3. ステップを設計する

- 並び順は**差分の上から順**（ファイル→ハンク順）。ただし理解の起点になる変更（エントリポイント・スキーマ・型定義）が後方にある場合は先頭に繰り上げてよい
- 1つの意味のある変更 = 1ステップ。機械的な連鎖（rename の全出現箇所など）は代表1箇所にまとめ、「他N箇所も同様」と書く
- `file:line` は**HEAD側の行番号**。削除のみの変更は、その削除を参照している周辺の残存行に置く
- 各ステップは「before→after」と「なぜ」を**1行以内**に要約する。収まらない論点は表の「なぜ」欄を短くし、詳細は補足へ回す
- 新規追加ファイルは冒頭に1ステップ置き、役割を説明してから内部の要点に進む

### 4. 全体像を図にする（非自明な変更では必ず）

変更の流れ（エントリポイント → 中間処理 → ゴール）を **ASCII 呼出図**でチャット直書きする（call-diagram 方式）。file:line を併記し、変更前後の分岐（before/after）も図内に示す。図が説明より長くなる小変更（rename・typo等）では省略可。

```
管理画面 / Staff API
   └─ send_line_broadcast  (新規boolean, default false)     app/controllers/...:209
          │
          v
NoticeContent#normal_publish_notice                        app/models/notice_content.rb:149
   └─ send_line_message_to(user_ids)   ← nil(暗黙broadcast)の廃止
        ├─ true (opt-in) → job(notice_content_id:)           → LINE broadcast
        └─ false (既定)  → store.line_user_ids_for(user_ids)
                              └─ job(to: [...])               → LINE multicast
```

### 5. 出力する

「結論1行 → ASCII図 → 変更点テーブル → 補足（必要なら）」の順でチャットに直接出力する。散文は補足以外で書かない。

```markdown
## <トピック>: 変更の流れ

**結論**: （1行で何を変えたか・何が起きるようになったか）

<手順4のASCII図>

| # | 変更点 (before→after) | 箇所 | なぜ |
|---|---|---|---|
| 1 | send_line_broadcast カラム追加 | db/migrate/...:1 | 既存レコードも安全側(既定)に倒す |
| 2 | バリデーション追加 | notice_content.rb:67 | 無効なflag単独trueを弾く |
| 3 | send_line_message_to 分岐反転 | notice_content.rb:263 | 暗黙broadcastの廃止 |

補足（図・表に載らない注意点のみ。無ければ省略・最大5行）:
- guard の理由（例: ジョブは `to: []` でも broadcast にフォールバックする）
- 要確認: precedingパスでの意図しない挙動など

ステップ数: N ｜ 概要: （1行）
```

- 1ステップ1論点。2つの考えが必要なら分割する
- 並び順は意図で決める（実行順・diffの上から順・重要度順など）。競合パスは順序を注記で明示する
- 未確認のまま書いたこと・確証が持てず確認が必要なことは「要確認」と明示する
- 補足が5行を超えるなら、図か表に戻す（文字の羅列にしない）
