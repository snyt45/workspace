# Diff

差分を上から順に辿り、変更の流れを理解できる形で解説する。レビュー（審査）ではなく、理解が目的。

## 3つの原則

1. **正確性は交渉の余地がない。** コードの挙動・ライブラリ仕様・関数の意味に不安があれば、推測を書く前に確認する。確認手段: 実コードを読む、`web_search` / `fetch_content` で仕様を調べる、重い調査は researcher サブエージェントに委譲する。**未確認のまま断言しない**。説明に誤りが1つあると、その後のステップすべてへの信頼が壊れる。
2. **各ステップに動機がある。** 単に「何が変わったか」ではなく「**なぜこの変更が必要なのか**」を語る。根拠はコミットメッセージ・PR説明・実装から取る。動機なしの変更は恣意的に見え、読者は定着しない。
3. **言葉より図が勝るときだけ図を使う。** 変更の構造（依存・呼び出し・フロー）が文章より図で伝わる場合のみ、`visualize` / `call-diagram` を使う。迷ったら省略 — ない図は偽の図より安い。

## 手順

### 1. 差分を取る

- PR番号/URLが指定されたら: `gh pr diff <PR>` と `gh pr view <PR>`（説明・コミット一覧）
- 指定がなければ: `git diff origin/main...HEAD`（3ドット）とコミット一覧
- 差分が空なら終了する

### 2. 理解を固める（正確性の検証）

説明を書き始める前に、変更の本質を正確に掴む:

- 変更がどの層（API / サービス / UI / DB）に及ぶか、何を達成する変更かを掴む
- 新しいライブラリ・API・パターンが登場したら、その挙動を確認する（実コード・ドキュメント・web検索）。知らない関数の意味を憶測で書かない
- 変更の意図がコミットメッセージ・PR説明から読み取れない場合は、該当コードと呼び出し元を読んで確認する。それでも不明なら推測ではなく確認事項として明示する

### 3. ステップを設計する

- 並び順は**差分の上から順**（ファイル→ハンク順）。ただし理解の起点になる変更（エントリポイント・スキーマ・型定義）が後方にある場合は先頭に繰り上げてよい
- 1つの意味のある変更 = 1ステップ。機械的な連鎖（rename の全出現箇所など）は代表1箇所にまとめ、note に「他N箇所も同様」と書く
- `file:line` は**HEAD側の行番号**。削除のみの変更は、その削除を参照している周辺の残存行に置く
- 各ステップに書くこと: 何が変わったか（before→after）、**なぜ変わったか**（コミットメッセージ・PR説明・実装から）、他ステップとの繋がり
- 新規追加ファイルは冒頭に1ステップ置き、役割を説明してから内部の要点に進む

### 4. 全体像を図にする（必要なときだけ）

変更の流れ（エントリポイント → 中間処理 → ゴール）がステップ列だけでは見えにくい場合、`visualize` スキルに図を委譲して1枚添える。呼び出し関係の説明が必要なら `call-diagram` スキルを使う。小さな変更では省略してよい。

### 5. ステップ列を出力する

チャットに直接出力する。各ステップに動機（なぜ）を含める:

```markdown
## <トピック>: 変更の流れ

1. `src/api.ts:6` — 何が変わったか（before→after）。なぜ: （理由）
2. `src/api.ts:12` — 前のステップからどう続くか
3. `src/schema.ts:3` — 型定義の変更（後方の変更の起点）
```

- 1ステップ1論点。2つの考えが必要なら分割する
- 並び順は意図で決める（実行順・diffの上から順・重要度順など）。競合パスは順序を注記で明示する
- 未確認のまま書いたこと・確証が持てず確認が必要なことは、文中で「要確認」と明示する

出力後に、ステップ数と概要1行を報告する。
